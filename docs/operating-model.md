# Operating model

## The unit of work

The Loop-Dee-Loup execution issue is a vertical slice: the smallest coherent outcome that one capable subagent can implement and verify end to end.

It does not assume that work naturally arrives as projects, epics, sprints, departments, or formal role handoffs. Those structures are allowed only when an observed coordination problem makes them cheaper than direct execution.

## Startup context budget

LDL's thin-orchestrator architecture depends on a fresh Claude Code session starting with very little context. `CLAUDE.md` imports `AGENTS.md` automatically, so both load into every session before it even knows which Issue it is supervising — that automatic startup surface is a bounded routing contract, not a place for accumulating prose.

Keep `AGENTS.md` limited to invariants needed for nearly every control decision: authority order, the vertical-slice/decomposition boundary determination, founder-interrupt conditions, the fixed chat report formats, and pointers to where the next layer of authority lives. Detailed implementation, review, polling, audit, and recovery mechanics belong in `docs/*.md`, an on-demand skill, or durable GitHub/repository state — loaded only once the current lifecycle stage actually needs them, not preloaded on the chance it might. Shortening prose while leaving the same material's full detail nowhere else is not a fix; the goal is a smaller globally-loaded semantic surface, not a smaller file with the same content moved into denser sentences.

Within the Loop-Dee-Loup source repository itself, `tools/check-startup-budget.mjs` (wired into CI as part of the `control-plane-paths` workflow) enforces a line-count budget on `AGENTS.md` and `CLAUDE.md` as a regression guard against silent re-accumulation. Neither the script nor that workflow is part of `tools/ldl-init`'s consumer-installable manifest — this is Loop-Dee-Loup's own guard on its own source files, not machinery an installed consumer repository also receives. The standard itself still applies wherever this document is read: a consumer repository that wants the same regression guard on its own installed `AGENTS.md`/`CLAUDE.md` can add an equivalent check as its own CI, the same way it owns its other repository-specific gates. The guard cannot judge whether an addition is a genuine universal invariant or a smuggled-back manual — that remains a review judgment — but a PR that legitimately needs more room raises the budget constant explicitly, in the same diff, rather than drifting past an unenforced target unnoticed.

The same "needed almost everywhere" standard applies to any other automatically-loaded material: a session's persistent auto-memory (`AGENTS.md` § Auto-memory boundary), unscoped `.claude/rules` (none currently exist in this repository), and globally-visible skill/persona metadata, which already stays to one-line frontmatter descriptions with full instructions loaded only on invocation.

## What belongs in one slice

A slice may cross UI, application logic, storage, configuration, tests, documentation, deployment, and verification. Layer count does not determine issue count. The outcome does.

A valid slice:

- produces one observable capability, correction, or closure condition;
- gives one session enough bounded authority to finish it;
- owns every internal activity required for completion;
- can be assessed independently against explicit acceptance criteria;
- leaves the repository and product coherent when merged.

These are normally internal steps, not separate issues:

- inspect the current implementation;
- decide a technical approach already bounded by product authority;
- modify different layers;
- add or update tests;
- update directly affected documentation;
- address valid inline-review findings;
- prepare the PR and durable handoff.

## Vertical vs horizontal decomposition

A plan that builds inventories, layers, subsystems, or enabling components across the whole outcome before producing a usable portion of that outcome has failed decomposition, even if every individual ticket looks bounded. Horizontal planning is a process failure, not a lower-priority planning style — it reduces the count of nominally missing pieces without producing anything usable.

**Vertical slice.** Produces a usable, observable portion of the parent outcome end to end — implementation, supporting assets, configuration, tests, documentation, migration, and verification for that bounded outcome, together.

**Horizontal activity.** Produces a layer, inventory, subsystem, or category of inputs without making any portion of the outcome usable — a component library before the first flow that uses it, an asset catalogue before the first shot that consumes it, every endpoint before the first UI that calls one.

**Legitimate enabling slice.** Removes a demonstrated blocker, or is a genuine prerequisite for the vertical slice immediately following it — and, either way, has its own independently verifiable outcome. A step that only prepares for a later slice and produces nothing independently verifiable on its own is speculative enabling work, not a legitimate enabling slice, no matter how small.

**Speculative enabling work.** Prepares broadly for possible future slices without evidence that the current slice needs it. Treat this as horizontal activity even when it is organized as several small tickets.

Horizontal activities can and often do exist inside a vertical slice — a slice may need a schema column, a shared component, or a reusable asset along the way. The rule is about default issue boundaries, not about banning foundations: a horizontal activity stops being a problem the moment it is scoped to, and delivered inside, the vertical slice that actually needs it.

### The decomposition self-check

Before creating or accepting a multi-issue plan, apply this test:

> If every planned issue were completed in order, when would the first independently usable, observable, and verified portion of the parent outcome exist?

If the answer is "only after several horizontal issues are all complete," the decomposition is presumptively invalid and must be reframed around vertical outcomes. Work through these questions to locate the failure:

- What usable outcome does each issue leave behind?
- Does the first issue materially exercise the real product or deliverable path?
- Are assets, schemas, services, libraries, docs, tests, or infrastructure being produced in bulk before their first concrete consumer?
- Could the plan instead build the first end-to-end path and create its dependencies just in time?
- Is enabling work justified by a demonstrated blocker, a safety boundary, an external dependency, or repeated reuse — or only by anticipated future need?
- Does acceptance verify the resulting capability in context, rather than merely the existence of components?

A decomposition session runs this check before finalizing its slice list (see Decomposition boundary below). An execution session runs it before treating "build the supporting layer first" as the shape of its own slice.

### Correcting a horizontal plan

The correction available depends on who finds the problem.

**A decomposition/planning session** that finds its own not-yet-dispatched plan is horizontal has full authority to fix it before any issue is dispatched:

1. preserve already-completed useful infrastructure as completed background work — do not discard it because the plan that produced it was flawed;
2. identify the next smallest usable portion of the actual parent outcome;
3. reframe a draft or existing open issue around that outcome where practical, rather than opening a parallel one;
4. move required assets and enabling tasks inside that slice as just-in-time work;
5. close or supersede redundant shopping-list or component issues rather than duplicating them;
6. create every currently foreseeable follow-on vertical slice, per the Decomposition boundary contract;
7. make dependencies express outcome order, not organizational layer order.

**An execution session** that discovers mid-slice that its own dispatched issue was itself scoped horizontally does not get the same authority. The active issue's explicit outcome and acceptance criteria are the highest authority (`AGENTS.md` § Authority), so the session may narrow or clarify its remaining work inside that outcome, but must not unilaterally rewrite the issue to a broader end-to-end outcome. If the smallest usable portion the session can identify would exceed what the dispatched issue already authorizes, that is a scope question, not a technical one: apply the founder interrupt conditions, and stay within the standing one-next-slice limit for genuinely new follow-on work (`AGENTS.md` § Session execution) rather than materializing a full follow-on slice list mid-slice.

### Before / after examples

**Software feature.** Before: separate issues for the backend endpoints, the frontend screens, and the test suite for one feature. After: one issue (or one small vertical sequence) that ships the first real user flow end to end, including the endpoint, screen, and tests it actually needs; later flows through the same feature become their own vertical slices, not the remaining layers of the first one.

**Media/content deliverable.** Before: an issue to inventory and generate every reusable asset a piece of content might need, followed by an assembly issue once the inventory is "complete." After: an issue that roughs in, sources the assets for, assembles, and verifies one contiguous segment; assets a later segment needs are produced just in time for that segment, and genuinely reusable by-products are kept rather than rebuilt.

**Legitimate infrastructure.** A migration that must run once, cannot be safely split per-feature, and blocks every subsequent slice (e.g. a schema change every later vertical slice depends on) is a valid independent enabling slice — it has demonstrated, immediate consumers rather than speculative ones, and it is itself independently verifiable (the migration runs cleanly and existing behavior still works).

### Issue acceptance criteria

Acceptance criteria such as "files exist," "assets are catalogued," "endpoints are implemented," "components are created," or "tests are written" are insufficient on their own. An execution issue must also demonstrate its bounded capability or deliverable working in its real context. The canonical issue-format contract (tracked in issue #202) governs issue-body structure; this section governs decomposition validity for execution issues, regardless of which execution-issue template is used. Founder-decision-form, audit-control, and idea-intake issues are control boundaries, not product slices — they are judged by the decision, verdict, or intake outcome they exist to produce, not by a working capability in context.

## When to create another issue

Create another execution issue only when there is a new independent outcome or a materially different context or authority boundary.

Separate control issues are allowed for:

- a founder decision;
- an external manual action;
- the repository's required post-merge acceptance audit;
- a distinct correction exposed after merge.

Do not describe those control boundaries as product slices when they are not.

## Critical-path decision forms

The Loop resolves product uncertainty in batches, not through a serial dialogue.

Before interrupting the founder, the session maps the currently visible path from the accepted outcome to the next implementable vertical slice. It gathers all founder-level choices on that path into one decision form. Technical choices already settled by repository authority remain with the agent.

A generated form contains:

- feature outcome and current verified state;
- the critical-path consequence of leaving the questions unanswered;
- all currently knowable blocking questions;
- mutually exclusive options;
- a recommendation and explicit tradeoffs for each question;
- a prefilled suggested answer the founder can accept or replace;
- per-question comments;
- one unrestricted final comments field.

The founder completes and returns the form as one unit. The session must not respond to each answer with another question that was already foreseeable.

### Form results

Completed answers are routed by meaning:

- **Settled decision:** compress into the parent snapshot.
- **Current vertical slice:** place in the slice contract and acceptance criteria.
- **Accepted independent outcome:** create the correct backlog candidate — a target repository's own prioritized backlog (e.g. Covenant's Burn Order) when the outcome is a product feature, or a `priority:*`-labeled GitHub Issue on Loop-Dee-Loup's own repository (`docs/priority-horizons.md`) when the outcome is about the Loop itself — with dependencies noted and, for Loop-Dee-Loup's own Issues, native `blocked by`/`blocking` relationships rather than an ordinal position. Never merge the two.
- **Rejected option:** retain only if necessary to prevent the same question recurring; do not create work.
- **Unclear answer:** include with any other newly exposed blockers in the next consolidated form.

A decision is not itself a backlog item. Only an accepted outcome requiring independent future work belongs there.

### Multiple forms

Another form is permitted only when an answer exposes a genuinely new blocker or dependency that was not reasonably visible earlier. Forms follow the critical path until at least one vertical slice is implementable.

Two consecutive completed forms without an implementable slice trigger diagnosis before another form. The session must identify whether the proposal is incoherent, authority is missing, or decomposition is too horizontal, then use that result to redirect the next critical-path form.

## Founder role

The founder owns:

- the desired product or business outcome;
- acceptance of initial feature proposals when intent is not already settled;
- answers to material product questions;
- decisions involving meaningful scope, UX, monetization, legal, privacy, security, reputation, cost, or irreversibility;
- credentials and manual actions that cannot be delegated;
- starting or resuming a Claude Code session with a short issue reference.

The final item is lightweight scheduling. The founder is not a status relay, prompt router, test runner, or routine approval gate.

## Version-one runner

GitHub is the persistent controller state. Claude Code is a disposable runner.

A normal invocation is:

> Run Loop-Dee-Loup issue #X.

The session reads the issue body and minimum repository authority, executes the vertical slice, records verified state and the next slice, then stops. A later session resumes from GitHub rather than from conversation history.

Version one deliberately does not include a daemon, queue worker, webhook dispatcher, or automatic session launcher. Those are infrastructure hypotheses to test only after the manual-dispatch loop proves useful.

## Session role

One Claude Code session owns one vertical slice:

- load the parent snapshot and identify the active slice — read that slice's own body directly only when implementing it inline rather than dispatching a fresh subagent worker per Two-plane Issue dispatch below;
- produce its complete outcome across all necessary layers;
- run specified checks;
- independently verify completion claims;
- route the change through available repository gates;
- refresh durable state;
- when this slice's completion exposes new follow-on work not already foreseeable at dispatch, prepare at most one next slice — see Decomposition boundary for issues that require multiple slices;
- stop.

## Two-plane Issue dispatch

A dispatched Issue can carry two distinct kinds of authority, and a session must not collapse them into one read.

**Control-plane authority** is lifecycle truth: accepted outcome, current state, the pointer to whichever execution Issue is currently authoritative, PR/review/audit status, blocker and founder-decision state. The `parent-execution` template is this plane. **Execution-plane authority** is the actual requirements, acceptance criteria, verification, and constraints a worker needs to produce the outcome. The `work-packet` (vertical-slice) template is this plane. Neither plane duplicates the other: updating lifecycle state does not require rewriting the execution spec into the control Issue, and updating execution requirements does not create a second detailed spec there.

**Immediate-dispatch gate.** This is the normal path and governs the sequence before any fallback or direct-inspection reasoning below is even considered. `tools/orchestration/ready-dispatch-gate.mjs` (issue #321) mechanically evaluates whether the control Issue already supplies all of the following, read directly off its recorded fields:

- state READY specifically — not EXECUTING, VERIFYING, REVIEW, AUDIT, CORRECTION, or any other lifecycle state; those mean the control Issue is already mid-cycle and should continue its own current step, never receive a fresh immediate dispatch;
- one current execution pointer;
- a settled route (executor/persona, if routing applies);
- blocker: none;
- founder decision: none;

On `READY_TO_DISPATCH`, the orchestrating session dispatches the worker immediately by reference — Issue number, controlling Issue, and route, taken from the gate script's own output — without first performing execution-Issue inspection, repository reconnaissance for implementation planning, decomposition analysis, related-Issue mechanism comparison, sizing/complexity analysis, or implementation planning. Those steps belong to the execution worker once dispatched, under the thick execution contract, not to the controller deciding whether to dispatch. Wanting to become more confident before handing off is not, on its own, a reason to perform any of them — a control Issue carrying a blocker or an unresolved founder decision is not dispatch-ready merely because it also carries an execution pointer and a settled route; blocker and founder-decision state are separate, explicitly-checked fields, never inferred from the presence of the others.

Issue #368 split the gate's non-ready outcome into two disjoint verdicts, because collapsing them into one broad `NOT_READY` produced a live regression: control #301 carried `Lifecycle: BLOCKED` and an active Blocker — authoritative control state that had already answered the control question ("do not advance this work now") — and the old gate's `NOT_READY` result read, under this section's own prior fallback prose, as license to fall through into ordinary execution reasoning. The controller did exactly that, investigating and working around linked execution Issue #297 instead of stopping. `BLOCKED` (exit code 4) is now the gate's verdict whenever the control Issue's own parsed fields positively assert a stop — a blocking lifecycle value specifically (the ad hoc bullet convention's `Lifecycle: BLOCKED`, or the shipped `parent-execution.yml` template's `State: BLOCKED_FAILURE`/`State: BLOCKED_EXTERNAL`, since that template's own dropdown never offers the bare word `BLOCKED` — issue #370), a Blocker field that was found and is not the "none" sentinel, or a Founder-decision field that was found and is not "none" — and it carries only that reason, sufficient for a concise blocked/founder-interrupt handoff with no second read. On `BLOCKED`, the orchestrating session stops immediately: it must not read the linked execution Issue, perform repository reconnaissance, attempt to resolve or work around the blocker, or reinterpret the blocker as authorization for different work, regardless of how confident-looking the rest of the control Issue's fields are. `NOT_READY` (exit code 3, unchanged) now means only that the immediate-dispatch shortcut genuinely does not apply and nothing read asserts a stop — a mid-cycle lifecycle state other than `BLOCKED` (EXECUTING, VERIFYING, REVIEW, AUDIT, CORRECTION; these retain whatever continuation their own lifecycle stage already authorizes, per Watched lifecycle breakpoints below, and are not converted into a blocker merely by this split), an unsettled Route, a malformed/self-referential/multi-valued Execution pointer, or a control Issue shape the gate cannot classify at all (a legacy unsplit Issue) — for all of these, fall through to the Decomposition boundary/Direct-inspection fallback below exactly as before. The one exception: when the control Issue's Lifecycle is one of those five post-PR values, `NOT_READY`'s own "fall through and reason normally" language does not license free reasoning either — see Watched lifecycle breakpoints below, "Deterministic post-PR transition resolution", for the deterministic gate that governs those values instead.

Dispatch by reference stays by reference: do not read the execution Issue into the orchestrating session first, and do not reconstruct its requirements, acceptance criteria, or test plan into the subagent prompt — the worker reads the execution Issue and governing repository authority directly. Issue #283 (the #282 incident) is the record of this failure: a controller reconstructed most of a self-sufficient execution Issue into a bespoke subagent prompt and then also told the worker to read the same Issue, paying for one specification twice and loading implementation detail into the orchestrating session for no benefit. Pipe the gate script's JSON output into `tools/orchestration/format-dispatch-prompt.mjs` and use its stdout verbatim as the dispatch prompt, rather than composing one by hand: a live #321 proof (`docs/diagnostic-traces/615f2b4a-69eb-42f1-bef6-432a4e32f4dc.json`) recorded a controller with zero forbidden reads and zero reconnaissance that still hand-composed a 2554-character prompt by restating whole AGENTS.md sections into it, exceeding the diagnostic's 700-char reference-only threshold — a distinct failure mode from #283/#282's read-before-dispatch defect, since no execution-Issue-specific content ever left the control plane, but "possible requirement retransmission" all the same by the same size proxy. The fixed formatter removes the composition step's freedom to grow rather than relying on the orchestrating session to remember to stay terse.

Prose alone did not hold this boundary: issue #321 found two independent fresh controller sessions — one captured in `docs/diagnostic-traces/4dea0981-616a-4cea-96e2-fdd1183b1d29.json`, one recorded directly in control Issue #322's body — that each read a complete, gate-satisfying control Issue and then still read the linked thick execution Issue (and, in the first case, queried unrelated PRs) before ever dispatching, despite this section's prose already stating the required sequence unambiguously. `ready-dispatch-gate.mjs` is the smallest reliable guard raised in response: it makes exactly one read (the control Issue itself, via `gh issue view`) and returns a verdict, so the reconnaissance-bundling that produced both regressions has no code path left to occur inside the gate check itself. It is a check the orchestrating session runs and then acts on, not a dispatcher, task router, or persistent controller — it never calls the Agent/Task tool itself, and a session that ignores its verdict is still a prose-level failure this script cannot force-correct on its own. Live dispatch behavior is still verified by a fresh-session proof (per #283 and #321), not only by this script's own unit tests.

This does not change how subagents should be briefed for genuinely ambiguous or undocumented work — situational framing, prior findings, and specific file/line context still belong in the prompt when no durable spec covers them. It narrows only the case where a complete, self-sufficient execution Issue already exists: there, the Issue is the spec, and re-explaining it into the prompt is waste, not diligence.

**Legacy unsplit Issues.** Not every Issue is split into control/execution planes. If routing/control state (outcome, state, route, blocker) can be extracted from an unsplit Issue deterministically, do that instead of a full orchestrator read. If judgment is required, dispatch a fresh routing worker that reads the full Issue and returns only a compact projection — outcome shape, executor/persona, blocker state, authority conflicts — never a prose implementation summary — for the orchestrating session to act on. This fallback is not license to make a full orchestrator read routine for newly created or migrated watched work; prefer the split.

**Direct-inspection fallback.** An orchestrating session may read execution-plane authority directly to resolve a genuine exception: conflicting authority between the two planes, corrupt or missing control-Issue state, an Issue whose shape routing analysis failed to resolve, a worker escalation whose consequence cannot be judged from compact control state, or a founder decision whose exact wording matters to the next control action. This is an explicit exception path, not a routine one.

This list is closed, not illustrative. An orchestrating session must be able to name which listed condition applies before reading execution-plane authority; a diagnostic-sounding reason that is not one of the five — wanting to sanity-check a route the control Issue already records, gauge how large or complex the work is, judge decomposition shape, or compare mechanisms across related Issues — does not qualify, no matter how cautious it sounds. When the control Issue already satisfies the immediate-dispatch gate above, the orchestrator dispatches on those fields directly; it does not open the execution Issue to double-check them. Issue #283 is the durable record of a live regression against this boundary; its full incident detail belongs there, not in this reusable rule.

A session that read execution-plane authority without recording which of the five conditions it was invoking cannot be cited as proof that this boundary held for that dispatch — the read is indistinguishable from a rationalized one after the fact. A session invoking a genuine exception should name it at the point of reading, and that recorded rationale is what stands as its evidence, not the mere fact that the read happened. Separately, downstream lifecycle progress on the dispatched work — its worker completing, its PR reaching review or merging, its audit closing — is evidence for that work's own outcome, not evidence that the dispatching read observed this boundary; the two are independent and must not be substituted for each other.

**No message bus.** A worker's return to the orchestrating session stays compact and control-oriented — complete, blocked, founder decision required, or the next authorized transition — not a narrative of implementation detail for the orchestrator to relay into a later worker's prompt. When one worker's output is needed by another, put it in durable repository/GitHub state and reference it there, rather than routing it through orchestrator chat.

## Execution authority boundary

Issue #630, on the live PR #628 incident: an owner-authored Stage 1 guidance comment (`https://github.com/LouPineWays/Loop-Dee-Loup/pull/628#issuecomment-5705748185`) was intended only to guide the correction path Stage 1 was already running — informing an already-authorized worker, per Bounded review cycle. A Codex Cloud task instead read it as a write-mode assignment (`https://github.com/LouPineWays/Loop-Dee-Loup/pull/628#issuecomment-5705790753`): it bootstrapped a writable `work` branch, edited files, committed, and reached `make_pr`, with no second GitHub PR ultimately appearing. Nothing about the comment differed structurally from an ordinary Stage 1 finding; the failure is that content alone was sufficient to reach mutation, with no check for a durable authorization reference in between.

`AGENTS.md`'s Execution authority boundary states the resulting invariant: content — a comment, reviewer finding, task-start message, or any other model-visible text — may inform an already-authorized worker but can never itself authorize repository mutation. This section names the boundary's concrete mechanism, so it is provable rather than merely asserted.

**The execution-authority envelope.** Before its first mutation, a worker must be able to trace its authority to one of exactly three durable sources — never to comment/message content alone, even content that quotes or links a real Issue number:

1. **A control-plane dispatch.** Not one uniform shape — each pre-PR pipeline stage carries the exact envelope its own deterministic formatter already requires, per Two-plane Issue dispatch above: `ready-dispatch-gate.mjs`'s `READY_TO_DISPATCH` verdict threads the full `{controlIssue, executionIssue, route}` triple through `format-dispatch-prompt.mjs`'s `formatDispatchPrompt`; its `READY_TO_DISPATCH_PLANNING`/`READY_TO_DISPATCH_INTEGRATION` verdicts carry only `{controlIssue, executionIssue}` through `formatPlanningWorkerDispatchPrompt`/`formatIntegrationWorkerDispatchPrompt` (deliberately no `route`); and `READY_TO_DISPATCH_UNITS` carries `{unitCommentUrl, parentExecutionIssue, sharedContractUrl}` through `format-unit-dispatch-prompt.mjs`'s `formatUnitDispatchPrompt` (neither `controlIssue` nor `route`). `tools/orchestration/execution-authority-gate.mjs` classifies each shape directly (`control_plane_dispatch`, `planning_dispatch`, `integration_dispatch`, `worker_unit_dispatch`) rather than requiring every pre-PR worker to reconstruct the implementation worker's three-field triple (Stage 1 review finding on PR #637: the prior wording here claimed one uniform envelope threaded verbatim through both formatters, which is not what either formatter actually emits).
2. **An explicit founder chat instruction.** The Version-one runner path — a founder starting or resuming a session with a terse issue reference, or a direct founder request inside an active session (Founder interrupt conditions). This is the one source with no GitHub-side artifact; its authority is the founder's own words in the current conversation, not a re-derivation from repository state.
3. **An authorized bounded-review-cycle correction dispatch.** `next-review-transition-gate.mjs`'s `STAGE1_CORRECTION_REQUIRED`/`STAGE2_CORRECTION_REQUIRED` verdicts, dispatched by reference to the PR or Audit Issue only — never the finding/audit narrative restated (Watched lifecycle breakpoints, "Deterministic post-PR transition resolution"). A control-Issue reference is optional here, not required: the genuine legacy/no-thin-control direct-reference shape both correction prompt formatters already support (`controlIssue: null`) remains authorized on the PR/Audit Issue reference alone.

A comment that merely names one of these references — "dispatch execution Issue #630 per controlling Issue #631" — is still content, not authority: the reference has to resolve through the actual gate/dispatch machinery above, not be taken on the comment's word. This is why PR #628's guidance comment could not have been mistaken for authority under this boundary even though it discussed a real, in-flight correction — nothing about a comment's own text, however accurate, substitutes for the gate read.

**Neighboring controls stay distinct.** #462/#463 governs whether comment content may enter an already-authorized worker's context at all (trust/provenance); this boundary governs whether content — trusted or not — can manufacture authority to mutate. #555 governs a narrower, already-specialized case (new Issue creation) and is not broadened by this section. `@codex review` remains reviewer-only per Code Review Rules (#86/#626): it never gains implementation authority merely because this boundary exists, and a blocked mutation attempt from a reviewer invocation remains evidence the reviewer-role boundary worked, not evidence of a gap here.

**Mechanical regression coverage.** `tools/orchestration/execution-authority-gate.mjs` exports `classifyExecutionAuthority(trigger)`, a pure classifier over trigger shapes matching the three sources above — `control_plane_dispatch`, `planning_dispatch`/`integration_dispatch`/`worker_unit_dispatch` (the pre-PR pipeline's own narrower envelopes, source 1), `founder_direct`, and `correction_dispatch` — plus the denied shapes (`comment`, `task_start_from_comment`, `codex_review`, and any unrecognized origin, which fails closed by default). Every authorized shape validates its required fields at the same strength the deterministic dispatch formatters already enforce (positive integer GitHub references, non-empty trimmed strings, GitHub issue-comment permalinks), so a structurally malformed truthy value (`controlIssue: "not-an-issue"`, `route: []`, an object-valued `founderInstruction`) fails closed rather than being classified as authority. Its tests reproduce the PR #628 comment shape and the `task_start_from_comment` shape as the negative case, this correction's own `{controlIssue: 631, executionIssue: 630, route: "bounded implementation worker / control-plane correction"}` dispatch as the positive case, and each pre-PR/direct-reference-correction shape plus its malformed-field failure mode — proving the concept mechanically rather than only asserting prose. This is deliberately not a runtime interception layer for any external platform (#630's own non-goal: LDL cannot repair Codex Cloud's upstream comment-to-task behavior) — it is the reusable, testable shape of the authorization check any LDL-governed worker already performs by following Two-plane Issue dispatch and the bounded review cycle as written. GitHub/provider write-permission scoping remains a valid defense-in-depth backstop underneath this boundary, not a substitute for it.

## Watched lifecycle breakpoints

Two-plane Issue dispatch above splits control-plane and execution-plane authority for a single dispatch. The same split holds across an entire watched outcome's lifecycle, not merely across one worker's reading of it:

> **Durable lifecycle/control state persists across the Issue lifecycle. No reasoning context — orchestrating controller or execution worker — persists across a genuine lifecycle breakpoint.**

> **The thin control Issue is the continuity surface a fresh controller resumes from. Workers read the thick execution Issue for their own stage. Lifecycle truth and execution truth remain separate.**

Issue #374 corrected this invariant on live evidence from the #368/#369 → PR #370 → audit #371 → correction PR #372 → re-audit #373 lifecycle: one controller context remained the reasoning owner across Stage 1 polling, finding verification, correction dispatch, merge, Stage 2, a NOT CLEAN correction PR, another Stage 1, another merge, re-audit, and closure, while only substantive workers underneath it were fresh. That was a faithful reading of the prior wording below this paragraph — "the orchestrator persists across the Issue lifecycle" — but the live run showed that wording is too weak a context-isolation boundary: it let "the orchestrator" mean the conversational/model context rather than the durable control state recorded on the thin control Issue. Persistence now means durable control responsibility on that Issue, never a retained reasoning context. This preserves everything #286/#299 got right — the two-plane split, reference-only dispatch, fresh substantive workers, the compact worker-return protocol, deterministic polling/state detection, fresh Stage 2 independence, and durable GitHub/repository state over conversational handoffs — while correcting only the persistent-orchestrator-context assumption.

The `parent-execution` (thin) / `work-packet` (thick) template pair established above for a single dispatch is the concrete mechanism this section operates over across time: the thin control Issue is the durable object a founder "watches" (functionally, `watch #12345`) and each fresh controller reads for the whole lifecycle; the thick execution Issue is what each substantive worker reads to perform its stage. Legacy unsplit Issues use the same compact-projection fallback already described above under Two-plane Issue dispatch — this section adds no second fallback.

Treat each of the following as a fresh-context boundary: both the controller observing/routing the transition and any worker performing it reconstruct their stage only from durable state, never from a prior controller's or worker's conversational context.

1. **Initial implementation → first PR.** The implementation worker's job ends once the PR and its required durable evidence exist (`docs/bounded-review-cycle.md`'s Entry check and Stage 1 steps 1-2). Do not preserve that worker merely because the PR may later draw review feedback. The controller that dispatched the worker ends here too, once the PR/control reference is durable, rather than remaining to watch Stage 1 in the same reasoning context — `AGENTS.md`'s Context-cost boundaries already treats the Stage 1 review request as a natural fresh-session boundary for the orchestrating session; this extends the same boundary to the worker that produced the PR. This breakpoint is not left to prose alone: issue #286 found a reproduction (`watch #311` → execution #310 → PR #317 → Stage 2 Issue #318) where an implementation worker correctly followed AGENTS.md's Session-execution "continue mechanically ... until CLEAN completion" instruction (since narrowed by issue #374) straight through Stage 1 wait, merge, and Stage 2 initiation, because nothing in its dispatch prompt scoped that instruction back down to this boundary. `tools/orchestration/format-dispatch-prompt.mjs`'s fixed template now includes an explicit stop-at-PR clause for exactly this reason — the enforcement point is the dispatch prompt itself, not a reviewer's memory of this section.
2. **PR review/fix.** A fresh worker handles review feedback or another actionable PR state, reconstructing only from the thick execution Issue, the PR, current review comments/findings, current repository state, and governing review authority (`docs/bounded-review-cycle.md` Stage 1) — never from the implementation worker's conversational state. One coherent response to one review round stays with one worker; do not rotate workers per individual comment (`docs/bounded-review-cycle.md` Stage 1 step 6; `AGENTS.md`'s Subagent dispatch). The controller observing this round does not remain the reasoning owner while waiting on a response either: a bounded deterministic check (`poll.mjs`) may run inside a fresh invocation, but once the round's durable outcome — a fix applied, or Stage 1 satisfied — is recorded, that controller ends. Issue #576 (the live #571/PR #573 reproduction): when a fix reaches Stage 1 satisfaction without a second Codex round via `docs/bounded-review-cycle.md`'s Correction-satisfied disposition, "recorded" means projected *and verified* — via `tools/orchestration/finalize-correction-breakpoint.mjs`, mirroring breakpoint 3 below's `finalize-audit-breakpoint.mjs` — before the correction worker reports or stops, never left for a prose reminder to enforce; a worker that commits and pushes the fix but never durably persists the `correction-satisfied` disposition leaves a fresh controller re-reading a control Issue that still looks unreviewed.
3. **Merge → Stage 2 audit.** Stage 2 already "start[s] the audit from a fresh independent context" (`docs/bounded-review-cycle.md` Stage 2 step 2). The thin control Issue records only the merged identity and the Stage 2 Audit Issue reference; it does not accumulate Stage 1 repair narrative. The controller that observed Stage 1 satisfied, merged, and triggered Stage 2 ends once that reference is durable — it does not carry the pre-merge/Stage-1 context through the audit wait or result. Issue #586 (live #582/PR #583): before merging at all, the ordinary (first-round, no-correction) Stage 1 satisfaction itself must be projected *and verified* — via `tools/orchestration/finalize-stage1-satisfied-breakpoint.mjs`, the ordinary-path sibling of breakpoint 2's `finalize-correction-breakpoint.mjs` — so `tools/review-watch/stage2-control-plane-ci-head.mjs` can later resolve the exact pre-merge head from durable state rather than failing closed once the PR has already merged. Issue #561 (live #559/#445/PR #558): "that reference is durable" means projected *and verified* — via `tools/orchestration/finalize-audit-breakpoint.mjs` — before the reviewer trigger is posted, never merely created. A controller that posts the trigger first and projects the control state afterward lets a fresh Stage 2 auditor observe stale `Lifecycle: REVIEW` for no reason but ordering.
4. **Stage 2 NOT CLEAN → correction → re-audit.** A fresh correction worker performs the authorized correction (`docs/bounded-review-cycle.md`'s NOT CLEAN handling under Verdict handling). The subsequent re-audit must be performed by a *different* fresh audit worker, again starting from Stage 2 step 2's fresh-independent-context requirement — the correction worker must never become its own re-auditor. This is the same independence boundary Stage 2 already exists to enforce: a correction worker auditing its own fix would collapse execution and independent-assurance authority into one context, which is exactly what Stage 2's fresh-context requirement exists to prevent. The controller that observed and routed the NOT CLEAN verdict does not persist into the correction PR lifecycle either; a fresh controller resumes from the audit issue's recorded verdict to dispatch the correction, then ends at breakpoint 1 above for that correction PR, recursively through breakpoints 2-4 as needed.
5. **CLEAN / terminal blocked / founder interrupt.** Once `docs/bounded-review-cycle.md`'s Verdict handling records a CLEAN disposition, or a terminal blocked/founder-interrupt state applies, the controller persists that terminal state to the thin control Issue and ends. No further reasoning context is required to close out this outcome. For a split thin/thick lifecycle reaching a backed CLEAN Stage 2 result, this persistence is itself mechanized (issue #542, closing the #486/#487/#538 gap): `STAGE2_CLOSE_READY`'s own `nextCommand` chains `tools/orchestration/close-control.mjs` after the work/audit close commands, so the thin control Issue's compact fields are rewritten to a truthful terminal state and the Issue is closed inside the same bounded transition — never left for the controller to compose by hand in a later reasoning context, and never requiring a second controller pass once work and audit are already terminal.

A controller resuming at a post-PR Lifecycle state runs this gate before any other tool call — exactly mirroring the discipline the pre-PR `ready-dispatch-gate.mjs` check already requires — and acts only on its single verdict, then stops per that verdict's `stopAfter` field. `AMBIGUOUS` is a founder-interrupt-eligible fail-closed stop (`AGENTS.md` § Founder interrupt conditions, "a failed safety/correctness gate with no authorized recovery path"), never license to fall back to loading broad history and improvising a multi-stage plan; free multi-step reasoning applies only there.

A control Issue's free-text "Next authorized transition" sentence remains useful for a founder skimming the issue, but it is never itself dispatch authority once this gate exists. #375's mid-cycle comment — "check PR #376 Stage 1 status ... verify/fix findings if any, then merge ... open the Stage 2 audit issue, trigger it, and end" — reads as a correct-looking sequence, and nothing mechanically stopped a controller from executing all of it in one reasoning context; that is the actual defect this section closes, on the same #397 evidence as the pre-PR pinning above. The authoritative source of "what happens next" for a post-PR control Issue is this gate's live verdict, never a prose paragraph, no matter how correct each individual step in it sounds. This does not reopen or redesign #374/#375's breakpoints — the five breakpoints above are unchanged and remain authoritative, and #294/#306's reference-only/no-message-bus semantics are unchanged and reinforced, not weakened, by routing dispatch through this gate's compact verdicts. This section only makes those already-settled invariants mechanically enforceable at the point live evidence showed prose alone did not hold.

Across all five breakpoints, the orchestrator's normal retained state stays the compact fields already named for a `parent-execution` Issue — control Issue, execution Issue, lifecycle state, route, PR, Stage 1/2 status, blocker/founder-decision flags — never copied execution requirements, diffs, test logs, review narratives, or audit reasoning; those stay in the thick execution Issue, the PR, and durable review/audit evidence, per Two-plane Issue dispatch's no-message-bus rule above.

Until issue #73 or another separately authorized launcher can start the next fresh controller automatically, founder-issued terse `work on #<control>` re-invocation is the scheduling mechanism between these breakpoints — a little manual scheduling, not a reason to keep the current controller alive. Waiting or polling for a response does not by itself justify an exception: a bounded deterministic observation may run inside a fresh invocation, but reaching the next durable breakpoint still ends that reasoning context, per `AGENTS.md`'s Context-cost boundaries.

## Execution-stage session boundaries

Watched lifecycle breakpoints above governs a watched outcome from its first PR through Stage 2 closure. Issue #294 and its founder clarification comment refine what happens *before* that section's breakpoint 1 — the interval between dispatching a thick execution Issue and the PR that enters `docs/bounded-review-cycle.md`. That interval is not one long implementation session. It is a short sequence of bounded sessions, each producing exactly one durable progress product and then ending.

Issue #397's live #408 reproduction found that describing this sequence only as informal stage names left it undispatchable: a control Issue recording `Lifecycle: READY_FOR_PLAN` was fed to `tools/orchestration/ready-dispatch-gate.mjs`, which returned `NOT_READY` purely because `READY_FOR_PLAN` was absent from the gate's own recognized states — licensing the controller to fall through to direct-inspection reasoning, exactly what this pipeline exists to prevent. The four pre-PR stages are therefore fixed `Lifecycle` field values the gate itself recognizes and dispatches on, not a separate informal description that can drift from the shipped script:

1. **`READY_FOR_PLAN`** (Plan). A thick execution Issue exists with no Plan Index yet, and `Route:` is `planning worker`. The gate dispatches that planning worker by reference only (control Issue + execution Issue references — nothing about the execution Issue's content belongs in that dispatch). The worker reads the thick execution Issue in full, determines the complete currently-foreseeable implementation decomposition, establishes any values or interfaces more than one unit depends on, persists the durable plan artifacts below, and returns only a compact `PLAN_READY <ref>` — then ends at its own fresh-session boundary, exactly like any other dispatched worker. Projecting that result into thin control state is a separate, later step, not something the same reasoning context performs before it ends: the *next* invocation of the gate against this control Issue re-probes durable state (`ready-dispatch-gate.mjs`'s `probeExistingPlan`, issue #498 unit 498-A) and, finding a valid Plan Index already exists while `Lifecycle` still reads `READY_FOR_PLAN`, returns `READY_TO_PROJECT_PLAN_READY` with a ready-to-persist `proposedBody` (current body plus `Lifecycle: PLAN_READY` and a `Plan:` bullet pointing at the canonical Plan Index permalink) instead of dispatching a second, duplicate planning worker. The 2026-09-10 #500 live trace is the exact reproduction this closes: a planning worker correctly published a plan and stopped, but #500 remained `READY_FOR_PLAN` / `Plan: none`, so the next invocation dispatched planning again and produced duplicate plan artifacts.
2. **`PLAN_READY`** (Route/Prepare). A durable `## Execution Plan Index (v1)` comment exists, parseable by `tools/orchestration/parse-execution-plan.mjs`, with no Dispatch Manifest yet. The gate runs `tools/orchestration/prepare-dispatch-manifest.mjs --execution-issue <N> --create` for a first manifest, or the same command with `--comment-id <id>` when updating an existing `## Dispatch Manifest (v1)` comment — a deterministic script invocation applying the cheapest-reliable dispatch tree to the units the plan already defined, not a model-worker dispatch. Stdout alone is not authoritative routing state: before recording `Lifecycle: ROUTED`, the controller must have persisted the manifest durably, verified the resulting comment reference, and actually written `Lifecycle: ROUTED` onto the control Issue via `write-control-snapshot.mjs` — completing that manifest run and then stopping without the write leaves exactly the stranded state Live reproduction C recorded (a verified manifest existed, but Lifecycle stayed `PLAN_READY`). Only then, and only when no unit lands on `REPLAN_REQUIRED`, may the Lifecycle advance to `ROUTED`; a `REPLAN_REQUIRED` unit is a fail-closed stop, never an authorized transition to `ROUTED`. The mirror image of `READY_FOR_PLAN`'s recovery above applies here too: a later invocation that finds `Lifecycle: PLAN_READY` but an already-verified manifest (`ready-dispatch-gate.mjs` reusing `verifyRoutedDispatchManifest` as a probe) returns `READY_TO_PROJECT_ROUTED` with a ready-to-persist `proposedBody` instead of re-running Route/Prepare and risking a second manifest comment. Issue #498 unit 498-B closes the #407/#408 and #454/#455 (via #434) reproductions of the opposite failure mode: a controller that received `prepare-dispatch-manifest.mjs`'s own fail-closed `REPLAN_REQUIRED` result out-of-band (its stderr/exit code) then read Worker Unit Contract bodies, the Shared Contract body, and router/parser source to diagnose the routing failure by hand instead of dispatching a planning-correction worker by reference. `ready-dispatch-gate.mjs` now runs that same routing computation itself as a dry probe (`probeReplanRequired`, reusing `prepare-dispatch-manifest.mjs`'s own `runPrepareDispatchManifest` with no `--create`/`--comment-id`, so nothing is persisted) before ever authorizing a fresh Route/Prepare run, and returns a distinct `REPLAN_REQUIRED` gate verdict — modeled on `next-review-transition-gate.mjs`'s `STAGE2_CORRECTION_REQUIRED` shape, carrying `stopAfter: true` and only compact reference-scoped fields (the execution/control Issue references, the Plan Index URL, the failing unit IDs, a reason composed solely from each failing unit's own mechanically-emitted note, and `route: "planning worker"` — a planning-correction is the same planning capability revisiting its own prior output, never a new worker role, and never a default/fuzzy route invented on the controller's behalf) — when one exists. The controller dispatches a planning-correction worker by that reference alone and stops; that worker reads the plan/unit authority directly, uses #497's deterministic writer/validator to persist a corrected plan, and returns only a compact confirmation. A later fresh invocation of this same gate against the still-`PLAN_READY` control Issue then re-evaluates exactly as it would for a plan that never hit `REPLAN_REQUIRED`, converging on the identical `READY_TO_RUN_DISPATCH_MANIFEST`/`READY_TO_PROJECT_ROUTED` boundary above — no special-cased "recovered from replan" verdict exists or is needed.
3. **`ROUTED`** (Execute). Unit dispatch is authorized only after deterministic durable verification: the Plan Index's `- **Dispatch manifest:**` field must be a non-`none` comment permalink, that exact comment must belong to the same execution Issue, it must carry `## Dispatch Manifest (v1)`, and its `- **Plan index:**` backlink must match the current Plan Index URL. Only then does the gate dispatch every currently `dispatch_ready=true` unit with no unmet prerequisite by reference off that manifest — genuinely independent ready units may be dispatched together as one wave, never a unit with an unmet prerequisite, and each concurrently-dispatched unit worker that writes or commits repository state uses `isolation: "worktree"` per § Concurrent subagent directory isolation below, so a wave never collides on one shared directory path; each unit's own dispatch prompt is composed with `tools/orchestration/format-unit-dispatch-prompt.mjs --execution-issue <N> --unit <UnitID>` (issue #498 unit 498-A names this formatter explicitly, closing the gap where `READY_TO_DISPATCH_UNITS` had no named next-stage consumer), never hand-composed. Issue #456 unit 456-B (the #537/#539/#540 live reproduction): "every currently `dispatch_ready=true` unit" means the gate's own reconciled `dispatchReadyUnitIds` list on the `READY_TO_DISPATCH_UNITS` verdict, not a raw re-read of the manifest comment's `dispatch_ready=` flags — `ready-dispatch-gate.mjs`'s `verifyRoutedDispatchManifest` excludes any entry whose own Worker Unit Contract already records `State: DONE`, since a manifest's `dispatch_ready` flag is dependency-readiness computed once at Route/Prepare time and is never itself re-derived per wave. Each worker reads its own unit contract plus the durable authority it points at, writes durable repository state, and records a compact completion/blocker state on its own contract. A unit dispatched with `isolation: "worktree"` records `State: DONE` only once its commit/branch reference is also captured in its own contract's Durable output/state expected field (§ Concurrent subagent directory isolation below) — a unit that produced repository changes under isolation but cannot record that reference has not reached `DONE`. Re-evaluate for the next wave once a wave's units are all `DONE` per their own contract's State field, re-read live, never cached; once every plan unit is `DONE`, the Lifecycle transitions to `EXECUTION_COMPLETE`.
4. **`EXECUTION_COMPLETE`** (Integrate/PR). Every plan unit is `DONE`. The gate dispatches the Integration/PR worker by reference only (control Issue + execution Issue references; that worker already knows, per `docs/bounded-review-cycle.md`, "Integration/PR worker", to read the Plan Index/Shared Contract/unit comments itself). That worker first merges every unit's durable commit/branch reference (§ Concurrent subagent directory isolation below) into its own integration checkout, then compares the plan against the actual repository result, repairs only authorized seams, verifies the integrated vertical outcome, opens the PR, and persists the PR/control reference — "every plan unit is `DONE`" means every unit's result is both recorded and actually integrated, not merely that every contract's State field says so while a completed unit's changes still sit unmerged on an isolated branch. This is the last pre-PR Lifecycle value this pipeline defines. Issue #444 unit 444-A (the #439/#440/#443 live reproduction): the gate dispatches the Integration/PR worker only when the control body's own `- **PR:**` and `- **Stage 1:**` bullets are both absent-or-`none` — a genuine PR and/or Stage 1 state already recorded, even while `Lifecycle` still reads `EXECUTION_COMPLETE`, instead chains to the existing post-PR transition path (`next-review-transition-gate.mjs`) rather than authorizing a duplicate Integration/PR worker.
5. **Review/Audit.** From the PR onward, Watched lifecycle breakpoints above already governs everything — Stage 1, merge, Stage 2, correction cycles, closure. This section adds no second lifecycle model there and no second set of breakpoints.

`READY` itself is unchanged by this pinning: an execution Issue simple enough not to need this pipeline still uses `READY` plus a settled executor route exactly as before.

Session count is not a success metric, and neither is unit count: a plan naming one implementation unit executed by one capable worker is a valid plan whenever decomposition would not earn its coordination cost. The invariant is one bounded durable progress product per reasoning session, with deterministic work pushed below reasoning wherever it is reliable. Sessions and subagents are orthogonal: a fresh session is not a substitute for isolating how-to context in a subagent, and a subagent is not a substitute for ending a session at a durable boundary.

### Single planning owner

Planning must not be fragmented across implementation workers. Exactly one planning context per execution Issue reads the thick Issue in full and owns the whole currently-foreseeable decomposition. Every later session operates from thin control state plus the durable plan, unit, and shared-contract references — not from rereading the thick Issue. A unit worker falls back to the thick Issue only when its own contract requires it or a concrete authority ambiguity must be resolved, never routinely "for context."

Deterministic routing is a separate stage precisely so it cannot become a second planning pass. It applies a mechanical tree to units the planner already defined; it does not redefine them, resize them, or invent new ones. When a unit cannot be routed without substantively reinterpreting the plan, that ambiguity is escalated explicitly on the plan (`REPLAN_REQUIRED` below) rather than silently resolved by the routing session — silent resolution is exactly how planning ends up distributed across several agents.

Shared decisions travel through durable state, never through the controller. The planner persists a shared contract once and each affected worker reads it; a worker never tells the orchestrator a value for the orchestrator to relay into another worker's prompt. Two-plane Issue dispatch's no-message-bus rule above applies to plan artifacts exactly as it applies to worker returns.

Each implementation worker's instruction surface is separate and need-to-know: the minimum authoritative information required to perform its own responsibility correctly, expanding only when a concrete dependency requires it. Do not include another unit's role or instructions for completeness, and do not copy the thick execution Issue wholesale into every contract to make each prompt look self-contained. If unit A genuinely needs unit B's detailed reasoning to proceed, that is evidence the decomposition boundary is wrong — recombine or replan rather than widening both contracts.

### Durable plan artifacts

These artifacts are comments on the thick execution Issue itself. They are durable execution state under one coherent Issue — not GitHub backlog micro-Issues, a task database, a queue, or a second tracker — and one execution Issue remains one backlog item no matter how many units its plan contains. Their headings and field names are fixed, because deterministic tooling parses them and several sessions write them at different times:

- **Plan Index comment** — heading line exactly `## Execution Plan Index (v1)`. Bullet fields: `- **Plan state:**`, `- **Parent execution issue:**`, `- **Shared contract:**` (URL), `- **Units:**` (one line per unit: `- <UnitID>: <state> — <one-line outcome> (<comment URL>)`), `- **Dependencies:**`, `- **Dispatch manifest:**` (URL or `none`), `- **Integration/PR route:**` (issue/PR ref or `none`). This is the compact projection a controller reads to identify the next authorized worker reference.
- **Shared Contract comment** — heading exactly `## Shared Contract (v1)`. Holds the constants, names, schemas, paths, interfaces, and compatibility assumptions more than one unit depends on, established once by the planner. Each unit contract points here instead of restating them.
- **Worker Unit Contract comment** — heading exactly `## Worker Unit: <UnitID> (v1)`, containing exactly these bold-label bullets, in this order: Unit ID, Parent execution issue, Required bounded outcome, Applicable role/capability, Authority/input pointers, Relevant shared-contract pointer, Prerequisites/dependencies, Files/surfaces expected to change, Observable completion condition, Verification required, Durable output/state expected, Interrupt/escalation conditions, State. When a unit is dispatched with `isolation: "worktree"` (§ Concurrent subagent directory isolation below), its Durable output/state expected field must record the resulting commit SHA and branch name, or state explicitly that no repository change resulted — the isolated worktree's own return value is transient to the dispatching turn, and integration reads this field rather than any conversational report of what the isolated worker did.
- **Dispatch Manifest comment** — produced by the Route/Prepare stage, not by the planner. Heading exactly `## Dispatch Manifest (v1)`, with `- **Plan index:**` (URL) and one line per unit: `- <UnitID>: route=<resolved route> dispatch_ready=<true|false> note=<escalation note or none>`.

**Unit-ID convention:** `<execution-issue-number>-<Letter>` — #294's own plan used `294-<Letter>` — stable for the life of that plan.

**State vocabulary** (the Plan Index's Plan state and every unit's State field use this fixed set): `PLANNED | ROUTED | IN_PROGRESS | BLOCKED | DONE | REPLAN_REQUIRED`.

**Edit-ownership rule** (avoids concurrent-edit races): a unit's own dispatched worker is the only writer allowed to edit that unit's own Worker Unit Contract comment, to update its State field and append a short completion/blocker note. No unit worker edits the Plan Index or Shared Contract comments, or another unit's comment. Only a Route/Prepare-stage session or the Integration/PR worker recomputes or refreshes the Plan Index comment, by re-reading current unit states — never from cached or remembered state.

**Planning-correction exception** (issue #618, closing the #441 live recurrence — a planning correction after PR #615 review needed to add a newly discovered blocking dependency, 441-C, to 441-B's already-published contract, and the only available mechanism at the time was a Dispatch Manifest note/override, exactly the second semantic planning surface #522/#294 already forbid): the edit-ownership rule above has exactly one narrow, field-scoped exception. A planning-correction session may change only the dependency-topology field — the Worker Unit Contract's own "Prerequisites/dependencies" bullet — of an UNDISPATCHED unit (State exactly `PLANNED` or `ROUTED`), and only through `tools/orchestration/correct-unit-dependency.mjs`'s deterministic, fail-closed mutation path: a complete replacement `dependsOn` unit-ID set, never free-form prose or an incremental "add one more" delta. It reuses `dependency-grammar.mjs`'s own canonical serializer/parser (the same authority `format-execution-plan.mjs` and `prepare-dispatch-manifest.mjs` already share) and locates-and-replaces exactly that one bullet's span in the comment's raw current body, so every other field — outcome, capability, authority pointers, verification, files/surfaces, and especially State/completion notes — is preserved byte-for-byte and mechanically verified unchanged before success is ever reported. It refuses a target unit already `IN_PROGRESS`, `BLOCKED`, `DONE`, or `REPLAN_REQUIRED`: that unit's own dispatched worker (or its own prior escalation) owns its contract exclusively from that point on, and this mechanism never races or overwrites it. It rejects an unknown/self/malformed/duplicate dependency ID and any replacement set that would introduce a dependency cycle, before ever writing. A correction needing broader semantic change creates or replans a replacement unit instead of stretching this exception. The Dispatch Manifest itself remains derived Route/Prepare output, never a second semantic planning surface: once a corrected dependency is durably persisted this way, `prepare-dispatch-manifest.mjs` re-derives `dispatch_ready` from the live comment on every ordinary subsequent re-run, so no manual manifest override is ever required or permitted again. Stage 1 review finding on PR #620 (P1): a stale `dispatch_ready=true` entry computed before the correction must not be left to outlive it either — if the Plan Index already names a real Dispatch Manifest when the correction lands, `correct-unit-dependency.mjs`'s own last step regenerates that one existing manifest comment through `prepare-dispatch-manifest.mjs`'s own `runPrepareDispatchManifest`, so the corrected topology is reflected before the script ever reports success rather than left as a manual follow-up step; no manifest yet needs no such step, since an ordinary first Route/Prepare run already computes correctly from the already-corrected contract.

A unit that discovers it is incorrectly bounded records `REPLAN_REQUIRED` on its own contract with the reason and stops; recombining units, escalating one to a stronger executor, or otherwise revising the plan preserves current durable state and the parent execution Issue's scope, and does not require creating another backlog Issue solely for execution granularity. Escalate to the founder only when the new information creates a genuine founder-level decision under `AGENTS.md`'s Founder interrupt conditions.

### Concurrent subagent directory isolation

Issue #441's founder-confirmed live reproduction established the substrate invariant this section reconciles LDL with: exactly one live Claude Code session or process owns an exact directory path at a time; a second launch at that same exact path fails closed as a deterministic path lock (`Another Claude Code session is already active in this directory`), regardless of whether the current owner is idle or has already done real work; a different directory path — including a different worktree of the same repository — is unaffected and may proceed concurrently; and archiving/terminalizing the owning session releases the path for immediate reuse. `list_sessions` is not a complete occupancy inventory, since a directly-opened session invisible to that list can still hold a path lock. This is not a global or repo-wide Dispatch-capacity limit and never an idle-vs-active distinction — treat it purely as path ownership.

Direct source inspection (`docs/diagnostic-traces/441-a-idle-session-capacity-diagnosis.md`, re-confirmed by `docs/diagnostic-traces/441-d-exact-path-lock-reconciliation.md`) found no session-count, slot, or capacity concept anywhere in `tools/orchestration/` or `tools/review-watch/`, and no LDL script launches a top-level Code/Dispatch session at all — that action is exclusively the founder's, performed directly through the CCD app, a surface this repository's code cannot reach and does not need to correct: the founder's own reproduction already shows the substrate enforcing the invariant correctly there.

The one surface this repository does author that can violate the invariant is subagent (Agent-tool) dispatch whose writer lifetimes overlap. The `ROUTED` (Execute) stage above authorizes dispatching every currently `dispatch_ready=true` unit "together as one wave" whenever the units are genuinely independent — concurrently-running subagents, each free to write, commit, and open work in the repository. Left without directory isolation, overlapping writers default to sharing the orchestrating session's own working directory, reproducing the same "independent concurrent work colliding on one path" failure one level down from the top-level-session layer the founder observed. This is not limited to writers dispatched in the same message: a writing unit worker still running from an earlier turn and a writing unit worker dispatched in a later turn overlap exactly the same way, and both would otherwise default onto the shared path — the relevant condition is overlapping lifetime, not whether the Agent calls happened in one message. Correction: whenever any writing subagent's lifetime overlaps another writing subagent's — same message or not — dispatch each overlapping writer with `isolation: "worktree"` so it owns its own distinct directory path and branch rather than a shared one. A single writer with no overlapping writing sibling — the ordinary case for most units and for `AGENTS.md`'s Session execution dispatches — needs no isolation change, since there is no sibling to collide with. Purely read-only concurrent dispatches (e.g. parallel research/Explore agents) need no isolation either, since they mutate nothing.

This closes the directory-collision gap with the smallest available mechanism rather than new capacity machinery: the Agent tool's own `isolation: "worktree"` option already gives each concurrent writer a distinct path, and its own automatic cleanup (removing the worktree when the dispatched worker made no changes, otherwise returning the path/branch for the controller to track) already satisfies "a released path becomes reusable" without a new LDL-side worktree-cleanup project. This did not add a scheduler, session-slot accounting, or a generalized worktree-cleanup pass over pre-existing stale worktrees — those stayed explicitly out of scope per #441's own non-goals — until #668 added exactly the narrow, deterministic startup-reconciliation pass described in § Worktree startup reconciliation below, scoped to the accumulation gap #441/#442 and the live #639/#638 collision actually demonstrated, not a general workspace manager.

Isolation alone only prevents the path collision; it does not by itself make an isolated writer's repository result durable. The Agent tool's returned path/branch is a transient value scoped to the dispatching turn, not durable state a later session or a later wave can rely on remembering. Correction: the dispatched unit worker itself persists its own commit/branch reference into its own Worker Unit Contract's Durable output/state expected field (§ Durable plan artifacts above) before recording `State: DONE` — a unit that produced repository changes under isolation and cannot record that reference has not reached `DONE`. The Integration/PR worker (`docs/bounded-review-cycle.md`, "Integration/PR worker") then merges every such referenced branch into its own integration checkout before it compares the plan against the actual repository result or verifies the integrated vertical outcome: `EXECUTION_COMPLETE` — "every plan unit is `DONE`" — means every unit's own result is both recorded and actually integrated, never merely that every contract's State field says so while a completed unit's changes sit unmerged on an isolated branch. This reuses the same fixed comment-based durable state the plan pipeline already authors, rather than a new provenance store or branch-management subsystem.

### Worktree startup reconciliation

Isolation above stops concurrent writers from colliding on one path. It does not stop the accumulation of disposable checkouts over time — every fresh Claude Dispatch session opens its own new `.claude/worktrees/<name>` checkout regardless of whether LDL asked for `isolation: "worktree"`, and none of that class of worktree was ever reclaimed once its session ended. #441/#442 first observed the resulting buildup; #639/#638/PR #640 reproduced a real failure from it — a fresh recovery session collided on branch `findings-require-formal-review-638` because a terminated Claude Dispatch session's worktree (`.claude/worktrees/new-session-20260906164725`) still owned it. Issue #667/#668 closes this with `tools/orchestration/worktree-preflight.mjs`, a deterministic fresh-session startup preflight — never a point an outgoing worker self-declares its own checkout disposable, per the founder's 2026-09-21 decision recorded on #667.

**Ledger.** A small JSON array lives at `<git-common-dir>/ldl/worktrees.json` — the one location every worktree of a repository shares and that survives any single worktree's own removal, so association metadata is never lost when its worktree is retired. Each entry records `path`, `gitCommonDir`, `sessionKey`, `branch`, `commit`, `controlIssue`, `executionIssue`, `pr`, `registeredAt`, `lastConfirmedAt`, `retiredAt`, and the last-known `outcome`. This is local resource-lifecycle metadata keyed by durable logical IDs (Issue/PR numbers), never machine-specific state promoted to GitHub authority.

**Registration at entry, while it is knowable.** Every invocation first upserts the entry for the checkout it is pointed at (its own cwd in the normal preflight form, or an explicit `--path` in the `register` form used to record an isolated Agent-tool worktree's path/lineage as soon as the orchestrating session learns it) — refreshing `lastConfirmedAt` and only overwriting `controlIssue`/`executionIssue`/`pr` when the caller actually supplies them, so a later plain reconciliation run never blanks out lineage recorded earlier. The path a run registers itself against is excluded from that same run's own reconciliation unconditionally, regardless of cleanliness or branch state.

**Reconciliation by logical lineage.** A live worktree under the managed root (default `<primary-worktree>/.claude/worktrees`; the primary/main checkout and anything outside this root are never candidates) is classified as follows:

- **No ledger entry (legacy, e.g. an old `new-session-*` Dispatch checkout predating this mechanism):** reclaimed only when independently proven safe — its branch tip must be a provable ancestor of the repository's own resolved default branch (durable elsewhere), and a non-forced `git worktree remove` must itself succeed. Directory-name pattern alone is never sufficient.
- **A ledger entry whose live branch no longer matches what was recorded:** retained as ambiguous.
- **A ledger entry whose logical lineage — `controlIssue`, else `executionIssue`, else its own `sessionKey` as a fallback no other entry can ever share — has not been superseded** by another entry recording a different path for the same lineage more recently: retained as active. A lone predecessor nobody has proven obsolete is left alone.
- **A superseded entry:** eligible. Safety itself is delegated to git, never reimplemented here — `git worktree remove <path>` without `--force` already refuses a dirty, locked, or otherwise-unsafe worktree, so an eligible-but-unsafe candidate is simply retained with git's own refusal reason recorded, and a locked candidate is checked and skipped before the attempt.

This is exactly how the correction-chain scenario resolves (#668 requirement 6, the #639/#638 reproduction): when a fresh session for the same `controlIssue`/`executionIssue` registers itself, the previous session's worktree for that lineage becomes superseded and is reconciled on that very startup, without ever touching a currently active or unrelated checkout. Removing a worktree only detaches its checkout directory — it never deletes the branch or any commit reachable from it, so PR/correction/Worker-Unit-Contract provenance survives retirement. `git worktree prune` runs once at the end purely to drop administrative metadata for checkouts already missing from disk; it is never treated as a substitute for the safety checks above.

A fresh session runs `node tools/orchestration/worktree-preflight.mjs [--control-issue N] [--execution-issue N] [--pr N]` once, as an early housekeeping step before substantive work — it is local resource lifecycle, not a lifecycle-state determination, and it never blocks, replaces, or is chained into the READY gate in `AGENTS.md` § Session execution. See `tools/orchestration/worktree-preflight.mjs`'s own module comment for the full CLI/ledger contract and `tools/orchestration/worktree-preflight.test.mjs` for the covered positive/negative/idempotence/legacy cases.

## Action envelope enforcement

Watched lifecycle breakpoints and Execution-stage session boundaries above establish *which* verdict a controller should reach at each transition. This section closes a distinct gap: independent live reproductions proved that reaching the correct verdict — including one already carrying a literal `stopAfter: true` field — did not by itself stop the same controller from doing more anyway.

- **#440** (no-action form): `next-review-transition-gate.mjs` returned `STAGE2_RESPONSE_UNUSABLE`, the controller explicitly stated the verdict stops immediately, and then continued into diagnosis, issue creation, source edits, a PR, and review in the same context.
- **#494** (action-bearing form): `STAGE2_REPORT_READY_TO_RECORD` authorized exactly one action (`record-verdict`). After that action produced its durable breakpoint, the same controller re-ran lifecycle logic, reached `STAGE2_CLOSE_READY`, and terminalized the chain in the same invocation.
- **#514** (healthy pre-PR form): one controller crossed `READY_TO_DISPATCH_PLANNING` -> `PLAN_READY` -> `READY_TO_RUN_DISPATCH_MANIFEST`/`ROUTED` -> `READY_TO_DISPATCH_UNITS` in a single context, then said it would wait for the dispatched unit to complete — despite each transition's own documented "record state, then end" contract and disposable/fresh-context semantics.
- **#500** (self-implementation form): `READY_TO_DISPATCH_UNITS` (bounded to a unit-dispatch handoff) was followed by free-form PR/repository archaeology and the controller directly editing source to address a Stage 1 finding it had no authority to implement.
- **#587 / PR #590** (correction-dispatch form, issue #607): `next-review-transition-gate.mjs` correctly returned `STAGE1_CORRECTION_REQUIRED` and the controller correctly dispatched the one authorized bounded correction worker by reference — then, in the SAME initiating context, restarted #587's own kickoff and re-ran lifecycle logic instead of stopping. The bounded envelope for `STAGE1_CORRECTION_REQUIRED`/`STAGE2_CORRECTION_REQUIRED` already generically rejected any action outside `["dispatch-correction-worker"]`, but this exact incident shape had no regression fixture, and the specific "restart this control Issue's own kickoff in the same context" behavior had no named action-kind. `restart-control-kickoff` (below) and a dedicated `action-envelope.test.mjs` fixture close both gaps.

The governing invariant (issue #486): **a deterministic lifecycle gate verdict is the complete action-authority envelope for the current controller context.** A no-action verdict authorizes zero further repository/GitHub operational work. An action-bearing verdict authorizes exactly its named action(s) and nothing else — never a second gate invocation, a further lifecycle transition, or a newly invented recovery sequence, even once the authorized action(s) completed correctly. This is not a second, looser policy layered on top of the verdict-by-verdict prose in `AGENTS.md` § Session execution and this document's own breakpoint sections above — it is the same boundary, made machine-checkable.

**Mechanism.** `tools/orchestration/action-envelope.mjs` holds one authoritative table mapping every verdict `state` string either gate script can return to an `actionEnvelope`:

- `mode: "none"` — zero further operational tool calls authorized (`AMBIGUOUS`, `NO_ACTION_YET`, `STAGE2_RESPONSE_UNUSABLE`, and `BLOCKED` in the ordinary case — see the `chain` bullet below for `BLOCKED`'s one conditional exception).
- `mode: "bounded"` — exactly the named `authorizedActions` (e.g. `READY_TO_DISPATCH_PLANNING` -> `["dispatch-planning-worker"]`; `STAGE2_REPORT_READY_TO_RECORD` -> `["run-lifecycle-gate-record-verdict"]`). Some bounded envelopes are context-sensitive rather than a fixed table row: `STAGE2_CLOSE_READY` derives its actual authorized actions from the concrete verdict's own `nextCommand` — a real gated work issue to close first vs. `ACCEPTED_NO_WORK_ISSUE`/an already-closed work issue, audit-only (Stage 1 finding on PR #534 — the fixed table row alone let the compliance checker accept a work-issue close the concrete verdict never authorized), and, per issue #542, whether `nextCommand` also chains `tools/orchestration/close-control.mjs` last (only ever true for a control-Issue-mode invocation with a real thin control Issue to terminalize, never a direct-reference `--audit-issue`/`--pr` invocation) — instead of always offering the superset. Bounded (and chain) compliance also enforces that each authorized action occurs at most once and in the envelope's own declared order — set-membership alone previously let a duplicated or reordered action sequence pass as compliant.
- `mode: "chain"` — authorizes exactly one further deterministic gate invocation, whose own verdict and envelope then govern what follows (`AUDIT_ISSUE_DETECTED` -> `["run-next-review-transition-gate"]`). A `NOT_READY` verdict carrying `postPrLifecycle` (one of `ready-dispatch-gate.mjs`'s five post-PR mid-cycle Lifecycle values — EXECUTING, VERIFYING, REVIEW, AUDIT, CORRECTION) is also classified as `chain` to `next-review-transition-gate.mjs`, per `AGENTS.md` § Session execution's own explicit post-PR exception to normal `NOT_READY` fallthrough (Stage 1 finding on PR #534: the table previously stamped unconditional `fallthrough` onto every `NOT_READY` result, this exception included, so the compliance checker could never detect reconnaissance or self-implementation performed instead of routing through the review gate). `BLOCKED` is likewise `chain` — to `["run-reconcile-control-blocker"]` — exactly when the verdict's own `blockerReconciliationEligible` field reads `true` (set by `ready-dispatch-gate.mjs` only when the Blocker field itself, never a Founder-decision-only or blocking-Lifecycle-only cause, is why the control is `BLOCKED`); any other `BLOCKED` verdict keeps the unconditional `none` row above (issue #437/#610 Stage 1 finding 1: `AGENTS.md` § Session execution's `BLOCKED` paragraph already conditionally authorized exactly one `reconcile-control-blocker.mjs` invocation followed by a fresh `ready-dispatch-gate.mjs` re-invocation, but this table's own unconditional `none` row for `BLOCKED` made both calls a violation under this same machine-checkable mechanism — the fix is this context-sensitive derivation, not a change to the documented prose).
- `mode: "fallthrough"` — `NOT_READY` without `postPrLifecycle` only; hands off to the Decomposition boundary / normal reasoning, matching `AGENTS.md`'s own explicit `NOT_READY` carve-out for every case other than the post-PR exception above. This mechanism does not police what a controller does after a fallthrough verdict beyond the fixed deny-list below, which `classifyEnvelopeCompliance` checks unconditionally, before the fallthrough short-circuit, for every mode including this one (Stage 2 audit finding on PR #534, issue #535: the deny-list check previously ran only after the fallthrough short-circuit, so a deny-listed action taken under ordinary `NOT_READY` was never evaluated at all). `repository-reconnaissance` is deliberately not a deny-list member (Stage 1 finding on PR #536, reviewed at c3c3a24): AGENTS.md's own fallthrough contract ("reason normally, including reading the issue's own body directly") requires exactly this action under ordinary `NOT_READY`, so an unconditional deny-list entry for it contradicted the carve-out it was checked "before" — the corrected deny-list leaves it authorized under fallthrough while every other mode still rejects it via the normal "not in this verdict's own `authorizedActions`" path (see below).

An unrecognized or absent verdict state (including the exitCode-1 operational-error shape neither gate script treats as a verdict at all) fails closed to `mode: "none"` rather than guessing at intent. `ready-dispatch-gate.mjs` and `next-review-transition-gate.mjs` both stamp this `actionEnvelope` directly onto every verdict object they return, so the boundary travels with the verdict a controller actually reads, not only with prose it might read past.

`classifyEnvelopeCompliance(state, actionsTaken)` is the deterministic, fail-closed compliance check: given a verdict state and an ordered list of canonical action-kind strings (e.g. `"dispatch-planning-worker"`, `"write-control-snapshot"`, `"rerun-gate"`, `"repository-reconnaissance"`, `"self-authorized-implementation"`, `"restart-control-kickoff"`) a controller actually performed after receiving that verdict, it reports `"compliant"` or `"violation"` with reasons — reproducible by any fresh reviewer, human or agent, from the recorded action list alone. A fixed deny-list (`rerun-gate`, `wait-for-completion`, `self-authorized-issue-creation`, `self-authorized-implementation`, `restart-control-kickoff`) is never authorized by any envelope regardless of mode, so a future table edit cannot silently legitimize one of these five specific failure modes via a copy/paste mistake. `restart-control-kickoff` (issue #607) names re-emitting the fixed `Starting #<issue>.` kickoff line for the same control Issue inside a context that already received a verdict for it — the #587/PR #590 incident's own "restart and re-run lifecycle logic" shape — and is unconditionally deny-listed because, unlike `repository-reconnaissance`, no mode (including ordinary `NOT_READY` fallthrough) ever legitimately re-kicks off a session already in progress. `repository-reconnaissance` is checked separately, mode-by-mode, precisely because ordinary `NOT_READY` fallthrough authorizes it while every other mode still rejects it (see above). `tools/orchestration/verify-action-envelope.mjs` is the CLI wrapper (`--state <VERDICT_STATE> --actions <comma-separated list>`, exit 0 compliant / 5 violation), usable by hand against a diagnostic trace's already-classified events or any equivalent recorded action log. `contextSensitiveEnvelopeStates()` (currently `STAGE2_CLOSE_READY`/`STAGE2_CORRECTION_PR_NEEDS_FINALIZATION`) names the states whose `authorizedActions` are derived from the verdict's own `nextCommand` rather than a fixed table row (see `getActionEnvelope` above); the CLI requires `--next-command <the verdict's nextCommand string>` for these and fails closed (exit 1) without it, rather than silently classifying against an absent `nextCommand` — Stage 1 review finding on PR #647 (issue #646, P2): omitting context previously misreported genuinely authorized actions as violations and, worse, certified an empty observed-actions list as "compliant".

`tools/orchestration/action-envelope.test.mjs` replays the #440, #494, #514, #500, and #587/PR #590 incident shapes directly as fixtures (the exact action sequences each live session performed), alongside every other verification class issue #486/#607 requires (founder/fail-closed stop, wait state, pre-PR blocker, action-bearing merge, action-bearing correction, the independent-defect-temptation deny-list, and the `NOT_READY` fallthrough carve-out) — a deterministic harness a fresh reviewer can run and extend, not a prose-only assertion that a model "should stop." A literal live multi-transition proving run (spawning a real Claude Code child process through several breakpoints and capturing its actual tool calls) is not currently reproducible on demand in this repository's own execution environment — see `docs/execution-boundary-experiment.md` for the credential-forwarding blocker that applies equally here — so this fixture-driven harness, plus the two gate scripts' own existing regression suites (unchanged and still passing with `actionEnvelope` added to their output), is the evidence this mechanism relies on until that constraint changes.

This mechanism does not replace the verdict-by-verdict prose in `AGENTS.md` § Session execution or this document's breakpoint sections — a controller still reads and follows that prose as its primary instruction. `actionEnvelope` and `classifyEnvelopeCompliance` exist so the same boundary is also checkable independently of whether a given controller run actually followed the prose, closing exactly the gap the #440/#494/#514/#500 incidents demonstrated: a correct verdict is necessary but was proven insufficient on its own.

**Live enforcement for the "none" mode (issue #641).** Everything above is post-hoc: it judges a recorded action list someone already produced, and does not by itself stop a live controller from calling another tool. The 2026-09-17 `#639`/PR #640 live reproduction proved this gap still mattered even without a completed violation: `next-review-transition-gate.mjs` returned `NO_ACTION_YET`/`stopAfter: true`, the controller explicitly recognized the contract required stopping, and still spent additional reasoning considering — though, in that run, not ultimately executing — reading `docs/bounded-review-cycle.md`, inspecting the gate implementation and issue content, invoking the `stage1-classifier-hardening` skill, and `spawn_task`, before eventually stopping. `tools/orchestration/action-envelope-hook.mjs` is a Claude Code `PreToolUse`/`PostToolUse`/`PostToolUseFailure` hook trio (wired in `.claude/settings.json`) closing exactly this residual gap for `mode: "none"` specifically: `PostToolUse` (Bash only) recognizes a completed invocation of `ready-dispatch-gate.mjs` or `next-review-transition-gate.mjs` (a structural "node <script>" token parse, quote-tolerant so a real `node "$CLAUDE_PROJECT_DIR/tools/orchestration/next-review-transition-gate.mjs" ...` invocation is recognized the same as an unquoted one, mirroring `action-envelope.mjs`'s own `parseChainedCommands` discipline — never a raw substring match), reads the verdict's own already-stamped `actionEnvelope.mode` off its one JSON stdout line, and — only when that mode is `"none"` — writes a small session-scoped marker under the gitignored `.claude/action-envelope-state/` directory (`LDL_ACTION_ENVELOPE_STATE_DIR` overrides it for tests). `PostToolUseFailure` (Bash only, Stage 1 review finding on PR #642) applies the identical detection to the distinct event Claude Code routes a Bash invocation through when the underlying command exits nonzero, times out, or errors — several no-action verdicts (`BLOCKED`, `AMBIGUOUS`, `STAGE2_RESPONSE_UNUSABLE`) intentionally exit nonzero while still printing a complete verdict, so `PostToolUse` alone never observed them. `PreToolUse` (every tool, unconditionally) denies any further tool call for that same session once the marker exists, citing the verdict and pointing at the fresh-invocation path. This does not hand-list `NO_ACTION_YET` or any other state — it reuses the verdict's own stamped `actionEnvelope.mode`, so `AMBIGUOUS`, `STAGE2_RESPONSE_UNUSABLE`, ordinary `BLOCKED`, and any future no-action state are covered automatically, and `bounded`/`chain`-mode verdicts (an authorized dispatch, merge, or gate chain) are never marked and so are never blocked by this hook — those remain governed by the post-hoc classifier above, unchanged. A denial does not itself terminate the turn — the model sees the reason and could attempt something else — but every further attempt in the same session is denied identically, so the outcome this hook actually guarantees is mechanical: zero further tool calls succeed in that controller context, provable from the marker and the hook's own denial log rather than from a transcript reading of whether the model chose to comply. The module is self-contained within `tools/orchestration/**` (Stage 1 review finding on PR #642: it previously imported `sanitizeSessionId` from `tools/telemetry/collect.mjs`, a path `tools/ldl-init` does not install, which would throw `ERR_MODULE_NOT_FOUND` wherever this hook module itself is installed without that import also being present). `tools/orchestration/action-envelope-hook.test.mjs` reproduces the `#639`/PR #640 sequence directly (the gate's `NO_ACTION_YET` verdict, then every one of the specific near-miss actions named above, each denied) alongside the `#486` action-bearing and blocker/founder-interrupt controls proving this hook does not over-constrain an authorized bounded/chain transition, plus the quoted-invocation and `PostToolUseFailure` regressions above.

This mechanism's live enforcement currently only fires where `.claude/settings.json`'s hook wiring itself is installed. Per issue #45 (`docs/consumer-contract.md`, "LDL-managed"), that wiring — like `tools/telemetry/` — is deliberately not yet part of `tools/ldl-init`'s managed set, so an installed consumer repository does not currently get this live, fail-closed enforcement; it still gets the post-hoc `classifyEnvelopeCompliance` mechanism above unchanged, since `tools/orchestration/**` itself is installed. Whether to extend `tools/ldl-init` to install a merge-safe `.claude/settings.json` (deepening a Claude-Code-specific control surface inside every consumer installation) or to instead formally scope this specific guarantee to Loop-Dee-Loup's own repository is an open founder-owned scope decision, not resolved here — see the Stage 1 correction discussion on PR #642.

## Transition-boundary contract

Watched lifecycle breakpoints and Action envelope enforcement above establish *which* verdict governs a transition and *what* a controller is authorized to do once it has one. This section states the distinct invariant that governs *how* any individual mutable-state-authorized durable mutation — a thin control Issue write, a merge, a lifecycle projection — must itself be sequenced so it cannot succeed on stale authorization or leave the next invocation consuming stale post-state (issue #601, control #600, closing the North Star authority #476 names for "deterministic transitions" and "independently verifiable autonomous state changes").

Five independent incidents each forced a bespoke fix before this invariant was named generally:

- **#492** — a classic TOCTOU: an audit's evidence-bearing context could change between evidence validation and verdict mutation.
- **#537** — a stale historical Stage 2 pointer could override the live open-PR phase; deciding from a remembered value rather than one re-derived fresh.
- **#576 / #586** — correction/ordinary-Stage-1 work could complete, and even a merge proceed, while the durable disposition state the *next* transition depends on remained stale — the effect outran its own required projection.
- **#581** — a lifecycle mutation could update one representation (the ad hoc `- **Lifecycle:**` bullet) while leaving another (the canonical `### State` heading) contradictory and stale.

Each of these is a case study, not reopened work: `finalize-pr-breakpoint.mjs`, `finalize-correction-breakpoint.mjs`, `finalize-audit-breakpoint.mjs`, and `finalize-stage1-satisfied-breakpoint.mjs` already correctly enforce this invariant for their own specific breakpoint, and `control-field-validator.mjs`'s `validateLifecycleStateCoherence` already correctly closes #581's own representation-drift gap. None of the four scripts or that validator were rewritten to establish this section; they are the evidence it generalizes.

**The invariant**, stated once so no future transition has to rediscover it by hand:

```text
fresh current state
→ validate authorization/preconditions
→ immediately before durable effect, revalidate the mutable witness
→ perform the bounded effect
→ persist/update the resulting lifecycle/control projection
→ fresh read-back verifies the postcondition
→ only then report success
```

A **witness** is any mutable fact that materially authorizes the effect (e.g. the control Issue's current Lifecycle, a PR's live head, a Stage 1 disposition). Revalidating it means re-running the identical authorization check against a freshly re-read value at the last practical deterministic boundary before the effect — not a second, differently-written check that could itself drift from the first. A changed or stale witness fails closed or deterministically recomputes; it is never silently consumed. Only mutable facts that can actually invalidate the authorization/effect relationship are revalidated — unrelated repository state, unrelated control-body fields, and full-repository/Manual rereads are explicitly out of scope, and semantic Stage 1/Stage 2 review is a separate, unweakened boundary this invariant does not replace.

**Shared enforcement seam.** `tools/orchestration/transition-guard.mjs`'s `commitControlBodyTransition` is the smallest reusable primitive implementing this exact pipeline for a control-Issue-body mutation, extending — never replacing — `write-control-snapshot.mjs`'s existing validated write (including #581's own coherence guard, reached unchanged through this seam). It exists so a *future* control-plane transition that does not yet have a bespoke finalize script can use this directly instead of hand-rolling the same compose/re-read/write/read-back-verify skeleton a sixth time; it does not migrate the four existing finalize-*-breakpoint.mjs scripts onto it (their own hand-rolled instances remain the correct, tested, unmodified implementation for their specific breakpoints). `tools/orchestration/transition-guard.test.mjs` proves the primitive would prevent or explicitly detect each case study's failure class as a regression fixture, without touching the historical fixes themselves.

Repository identity for the whole operation is resolved exactly once, before any read or write — reusing `ready-dispatch-gate.mjs`'s own `resolveRepoIdentity` when a caller omits `repo`, exactly like `write-control-snapshot.mjs`'s CLI entrypoint already does — so every read and the write always target the same repository rather than two independently-defaulted ones (Stage 1 review finding on PR #602: an unresolved default previously reached the writer only, so the writer failed even for an otherwise-valid transition). When a transition's material witness includes mutable evidence outside the control body itself (a PR's live head, a Stage 1 disposition — the examples above), the caller supplies a `fetchWitness()` function; the module — never the caller — re-fetches it fresh at both the initial and pre-effect boundaries and passes it to `compose` alongside the fresh body, so external evidence a caller captured once can never satisfy commit-time revalidation merely because the control body itself was unchanged.

**Non-atomic external effects** (e.g. a PR merge plus the control-state projection around it, which cannot be one atomic mutation) follow a deterministic resumable sequence rather than a single wrapped call: persist/verify any prerequisite transition state the effect depends on first, revalidate the live witness immediately before the external effect, perform exactly the authorized effect, then persist and read back the resulting projection before reporting completion. This is not a new mechanism — it is the exact ordering issue #561/#586 already established and "Deterministic post-PR transition resolution" above already documents (`finalize-stage1-satisfied-breakpoint.mjs` before `merge-pr` before `finalize-audit-breakpoint.mjs` before the reviewer trigger). An interruption between persisting prerequisite state and persisting the postcondition leaves a mechanically detectable, reconcilable partial state (the external effect's own live evidence — e.g. `gh pr view --json state` — disagrees with what the control body still records), never a silently misreported success; `finalize-stage1-satisfied-breakpoint.mjs`'s own `--recover` mode is the concrete precedent for reconciling exactly that shape.

**Telemetry-visible failure classes.** `TransitionFailureClass` in `transition-guard.mjs` names four deterministic result codes any transition guard's failure can be classified into, so a later telemetry surface can consume them without this slice building new telemetry infrastructure: `STALE_START_PRECONDITION` (authorization did not hold even at the initial fresh read), `WITNESS_CHANGED_TOCTOU` (it held initially but the witness changed by the commit boundary), `POSTCONDITION_PROJECTION_FAILED` (the effect's durable projection could not be established or confirmed written), and `POSTCONDITION_READBACK_MISMATCH` (the projection was written but a fresh read-back does not match what the effect was supposed to produce).

Retries are idempotent by construction whenever the authorization check itself treats the post-transition state as an authorized starting state (exactly how every existing finalize-*-breakpoint.mjs script's own `ALLOWED_*_LIFECYCLE` set already includes its own resulting value) — re-running composes the identical target body and the write is a safe no-op, never a duplicated effect.

## Live interrupt state and blocker reconciliation

Issue #437 (two live reproductions, #408 and #440): a thin control Issue's `- **Blocker:**` and `- **Founder decision:**` bullets are live current-interrupt state, never historical storage. A non-`none` value correctly makes `ready-dispatch-gate.mjs` return `BLOCKED` and stop the controller (issue #368's fail-closed invariant, unchanged and unweakened here — see `AGENTS.md` § Session execution's `BLOCKED` paragraph). The defect this section closes is different: nothing previously required that state to be cleared once the condition it recorded was actually satisfied or consumed, so a founder had to manually rewrite `BLOCKED`/non-`none` fields back to a ready state before an otherwise-authorized invocation could proceed.

**Canonical resolved forms.** A resolved `Blocker` or `Founder decision` reads exactly `none`, or `none — <compact reference>` when a short provenance note is useful (`isNoneSentinel` in `ready-dispatch-gate.mjs` already accepts both forms). Neither field is a diary: detailed history belongs in the thick execution Issue, PR/audit evidence, comments, or another durable provenance surface — the live field itself keeps only enough to say what was resolved.

**Founder decision clearing is a same-transition discipline, not new code.** A `Founder decision` is consumed synchronously, inside the same bounded transition that advances `Lifecycle` under it — a `finalize-*-breakpoint.mjs` script, `close-control.mjs`, or a session composing a body via `write-control-snapshot.mjs`. That composed body must set `Founder decision` to `none — <compact resolution note>` in the same write that advances the lifecycle under the founder's answer; `upsertControlBullet` already updates the bullet and any template `### Founder interrupt` heading atomically, so no new detection mechanism is required. Leaving the field non-`none` after the decision it recorded has already been acted on is the #408 defect class.

**Blocker-prerequisite grammar.** A `Blocker` naming an explicit, currently-unsatisfied prerequisite must use the canonical clause recognized by `tools/orchestration/blocker-grammar.mjs`: case-insensitive `Blocked by #N[, #N...].`, extracting every referenced issue number up to the first `. ` or end of field — the same stopping rule `dependency-grammar.mjs`'s `DEPENDS_ON_CLAUSE` already uses for `Depends on`. A control blocked this way must also carry, authored at block time rather than inferred later:

- `- **Blocked lifecycle:**` — the exact `Lifecycle` value to restore once every named prerequisite resolves;
- `- **Blocked route:**` — the exact `Route` value to restore, or the literal sentinel `unchanged` when `Route` does not need to change.

These fields exist because `ready-dispatch-gate.mjs`'s own `BLOCKED` convention (issues #368/#370) overwrites `Lifecycle` with a sentinel (`BLOCKED`, `BLOCKED_FAILURE`, `BLOCKED_EXTERNAL`), discarding the real pre-PR/post-PR value underneath; recomputing that lost value later by re-deriving it would be a second, drift-prone classifier, not a smallest-extension fix, so it is instead recorded explicitly once, at the moment the control is blocked.

A `Blocker` field that does not match this grammar — free prose, no recognized clause, the actual historical #440 shape — is not mechanically reconcilable and is understood by design as such: it fails closed to `AMBIGUOUS_BLOCKER` (below) rather than being guessed at from wording, tense, dates, or issue-number ordering.

**`tools/orchestration/reconcile-control-blocker.mjs`.** A standalone, explicitly-invoked script — not a change to `ready-dispatch-gate.mjs`'s own `evaluateReadyDispatchGate` fail-closed core — that runs only after the gate has already returned `BLOCKED` specifically because of a non-`none` `Blocker` (not only a `Founder decision`). It probes, then proposes, then writes, mirroring the existing `probeExistingPlan`/`close-control.mjs` shape:

1. Read `Blocker` the same way `ready-dispatch-gate.mjs` itself does — the ad hoc `- **Blocker:**` bullet, falling back to the shipped template's `### Current blocker` heading when the bullet is absent (issue #437/#610 Stage 1 finding 5: reading only the bullet left a template-created control's own heading-shaped `Blocker` permanently unreconcilable) — then parse it with `blocker-grammar.mjs`. `hasUnrecognizedBlockerWording` is checked first: any issue reference outside the recognized clause (e.g. `Blocked by #407. Also waiting on #408.`) yields `AMBIGUOUS_BLOCKER` rather than partially resolving against only the captured issue(s) (Stage 1 finding 3). No recognized clause at all, a missing/empty companion `Blocked lifecycle`/`Blocked route` pair, an unrecognized `Blocked lifecycle` value, or a `Blocked lifecycle`/`Blocked route` pair the live gate's own compatibility rule (`isRouteCompatibleWithLifecycle`) would reject also each yield `AMBIGUOUS_BLOCKER` with no mutation (Stage 1 finding 4).
2. For every named prerequisite issue, fetch its `state`/`body` (`gh issue view <N> --json state,body`, injected the same way `close-control.mjs` injects `ghIssueViewImpl`, for zero-network-access testability). An open prerequisite yields `INCOMPLETE_PREREQUISITE`. A closed prerequisite is further classified with `isAuditShapedBody` (`tools/orchestration/ready-dispatch-gate.mjs`, built from `lifecycle-gate.mjs`'s own `parseFormField`) and `parseStage2Verdict` (`tools/review-watch/lifecycle-gate.mjs` itself, imported directly — the same existing one-way exception to the `tools/orchestration` → `tools/review-watch` import direction `close-control.mjs` already uses): a closed Stage 2 Audit Issue must carry a recorded `Verdict` of exactly `CLEAN`, or it also yields `INCOMPLETE_PREREQUISITE` — a `NOT CLEAN`, `PENDING`, or malformed/missing verdict never unblocks merely because the Issue closed. An ordinary closed issue (not audit-shaped) satisfies the condition on closure alone. Issue #437/#610 Stage 1 finding 2: this deliberately uses `isAuditShapedBody` rather than the stricter sibling `classifyAuditIssue` (also in `ready-dispatch-gate.mjs`, used elsewhere for `AUDIT_ISSUE_DETECTED` classification) — `classifyAuditIssue` additionally requires `parseStage2Verdict` to already parse non-null, which let a closed prerequisite with the canonical audit headings but a missing/malformed `### Verdict` field fall through to "ordinary closed issue" and satisfy on closure alone. `isAuditShapedBody` detects the audit shape independently of verdict validity, so a malformed/missing verdict on a genuinely audit-shaped prerequisite still fails the same exact `=== "CLEAN"` comparison rather than silently passing.
3. Only when every named prerequisite independently satisfies step 2 does the script write anything — and immediately before that write, it repeats steps 1-2 against a freshly re-read control body, never the one read at the start of the invocation (issue #437/#610 Stage 1 finding 6: without this, a concurrent lifecycle transition landing during step 2's own network calls could be silently overwritten by a now-stale proposed body). Only once that fresh re-check also finds every prerequisite satisfied does it compose the body: via `upsertControlBullet`, sets `Blocker` to `none — <compact note, e.g. "#407, #408, #436 closed">`, `Lifecycle` to the recorded `Blocked lifecycle` value, and `Route` to the recorded `Blocked route` value (skipped when it reads `unchanged`) — persisted with `checkWriteControlSnapshot` (`write-control-snapshot.mjs`), never a raw `gh issue edit`. This is the one durable state mutation Required Behavior #4 in #437 asks for; a partially-satisfied set changes nothing.
4. Idempotent by construction: a `Blocker` already reading `none`/`none — ...` yields `ALREADY_UNBLOCKED`; an already-closed control Issue yields `ALREADY_TERMINAL` (mirroring `close-control.mjs`'s own precedent). Neither writes.

Result vocabulary and exit codes (mirroring `close-control.mjs`'s documented convention): `0`/`UNBLOCKED` (wrote a cleared body), `0`/`ALREADY_UNBLOCKED`, `0`/`ALREADY_TERMINAL`, `3`/`INCOMPLETE_PREREQUISITE`, `4`/`AMBIGUOUS_BLOCKER`, `2`/`REJECTED` (the composed body failed `write-control-snapshot.mjs`'s own field-local validation — e.g. an unrelated pre-existing corrupted field elsewhere in the body; mirrors `close-control.mjs`'s own `REJECTED` contract for the same write-before-validate guard, added by implementation unit 437-B alongside the vocabulary above), `1` operational error (missing args, unresolved repository identity, `gh` failure).

`Blocker`/`Founder decision` gained duplicate-bullet protection in `control-field-validator.mjs`'s `DEFAULT_CONTROL_FIELD_SPECS` (unit 437-B) via a new `pointerCheck: false` spec flag, not merely by omitting `expectedKind`: unlike `Execution`/`PR`/`Stage 2`, these two fields are never single-pointer values (a live value is free prose, e.g. `Blocked by #407, #408.` or a founder's own sentence), and the existing pointer-cardinality check inside `validatePointerFieldValue` would otherwise reject any such value outright regardless of `expectedKind`. `pointerCheck: false` skips only that trailing cardinality/kind check; the same exact-duplicate-bullet and near-duplicate-label protection every other canonical field already has still applies in full.

**Controller integration.** `AGENTS.md` § Session execution's `BLOCKED` paragraph names the one authorized action: when the gate's `reasons` name a non-`none` `Blocker`, the controller's one permitted step before treating `BLOCKED` as a genuine stop is exactly one invocation of `node tools/orchestration/reconcile-control-blocker.mjs --control-issue <N>`. `UNBLOCKED` means re-invoke `ready-dispatch-gate.mjs` fresh against the now-updated body and proceed from that fresh verdict. Every other result — including `ALREADY_UNBLOCKED`/`ALREADY_TERMINAL`, which mean the `BLOCKED` verdict itself was already stale in the opposite, error-prone direction and should not occur in the normal sequence — stops the session with the existing concise `BLOCKED` chat contract, unchanged. This never touches `evaluateReadyDispatchGate`'s own fail-closed logic; it adds exactly one deterministic, reference-scoped step to the existing `BLOCKED` path, and a `Founder decision`-only `BLOCKED` (no non-`none` `Blocker` present) has no reconciliation step to run — it remains a direct stop exactly as before. This authorization is also machine-checkable, not only prose: `ready-dispatch-gate.mjs` stamps the exact condition ("the Blocker field itself is the reason") onto the verdict as `blockerReconciliationEligible`, and § Action envelope enforcement's `BLOCKED` row derives a `chain` envelope (`["run-reconcile-control-blocker"]`) from it — never widened unconditionally — closing the issue #437/#610 Stage 1 finding 1 gap where this same authorized step would otherwise fail `verify-action-envelope.mjs`'s own compliance check.

**What this does not do.** Reconciliation clears durable readiness state only; it never itself launches a fresh coding session (#73/#379 remains the separate owner of automatic launching). It is invoked once per controller-observed `BLOCKED` verdict — never a recurring sweeper, queue, or background process. It does not reach backward from a prerequisite's own closing transition to proactively reconcile its dependents (that would need a reverse dependency lookup and is left to a future issue if evidence justifies it); the explicit controller-invoked step above already satisfies "without founder editing" because `ready-dispatch-gate.mjs` is already the mandatory first action of every session. And it does not extend to post-PR Lifecycle semantics (`EXECUTING`/`VERIFYING`/`REVIEW`/`AUDIT`/`CORRECTION`) beyond what `Blocked lifecycle`/`Blocked route` already cover generically — a post-PR-specific gap found during implementation is a `REPLAN_REQUIRED` on the discovering unit's own contract, not an improvised second mechanism.

## Decomposition boundary

Decomposition and execution are separate control boundaries. An issue completable as one bounded vertical slice executes normally under Session role above. For a control-plane issue, the Immediate-dispatch gate above runs first (this ordering is stated directly in `AGENTS.md` § Session execution, not only here, since that file is the automatically loaded startup contract): decomposition analysis applies only when that gate does not apply — to the execution work itself (inline slice execution or a legacy unsplit issue), never as a reassessment of a linked execution issue a satisfied gate already authorizes to dispatch by reference.

An issue that genuinely requires multiple independently executable slices triggers a decomposition session instead. Once that determination is made, the session must not begin implementing any resulting slice — not even the first one, and not "to save a session." Before it ends, it must:

1. apply the decomposition self-check above: ask when, if every planned issue completed in order, the first independently usable, observable, verified portion of the parent outcome would exist — if the answer is only after several horizontal issues are all complete, the plan is horizontal and must be reframed around vertical outcomes before proceeding, even though the finished plan would eventually be usable;
2. determine every currently foreseeable, implementation-ready vertical slice — not speculative work whose need depends on discoveries not yet made by an earlier slice;
3. create one self-sufficient execution issue for each slice (the vertical-slice template), containing enough of the outcome, constraints, acceptance criteria, and dependencies that a fresh session can execute it without reconstructing this conversation;
4. record genuine dependencies between those slices using GitHub's native issue relationships (Blocked by / Blocking), not free-text cross-references alone;
5. close the source issue as a durable decomposition record — retaining its objective, settled decisions, scope and non-goals, the resulting slice list, dependencies, and any unresolved external dependency — rather than leaving it open to sequentially point from one child to the next;
6. stop.

Do not create issues to mimic implementation steps, conversational turns, or organizational roles. Do not manufacture speculative future slices whose shape depends on an outcome not yet known — "every currently foreseeable slice" is not "every slice that might eventually exist."

A resulting slice begins only when the founder explicitly dispatches it in a fresh session (e.g. "Work on #123"). Creating a slice — including during the same decomposition session that just created it — does not authorize beginning it. Do not infer dispatch from having just created the issue.

Once dispatched, a slice runs autonomously per `AGENTS.md` § Session execution and the bounded review cycle until it reaches CLEAN completion or a genuine founder interrupt or unrecoverable blocker applies. CLEAN completion of one slice does not authorize beginning a sibling slice created in the same decomposition, even one that is now unblocked, obviously next, or has no remaining founder decision. The founder chooses which executable issue to dispatch next.

## Verification and autonomy

Autonomy begins after the founder dispatches the issue. It means completing the slice without routine questions or approvals. It does not mean bypassing controls.

A session may complete its slice only when:

- the whole slice outcome is present;
- acceptance criteria are satisfied;
- required checks pass;
- independent verification supports the handoff;
- the target repository's review and merge rules are satisfied;
- no interrupt condition applies.

A failed gate changes the state. It does not justify silently lowering the gate.

## Communication discipline

Claude Code chat is ephemeral and expensive. Use it only for control:

- acknowledge the issue briefly;
- link one consolidated decision form when founder input is required;
- ask a direct concise question only for a single unforeseeable blocker discovered mid-slice;
- report completion or the stopping state briefly.

GitHub holds detailed evidence, decisions, links, and the next slice. Avoid progress narration that duplicates durable state.

## Durable state

The parent issue contains current feature truth. The source queue contains priority and a link. Slice issues contain bounded execution contracts. Code and git contain shipped reality. Comments retain history but are excluded from normal retrieval.

This separation prevents the loop from turning either GitHub or an agent session into an ever-growing transcript.
