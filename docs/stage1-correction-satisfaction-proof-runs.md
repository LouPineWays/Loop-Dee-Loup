script's own header comment for detail. Scenarios 3, 4, 5, and 7 were unaffected in outcome by
either change and are re-recorded below only because they share the same fixture script
(`454-constructed-fixtures-exercise.mjs`) and constants as Scenario 6. Scenarios 1 and 2 use
their own separate fixture scripts (`454-scenario-01-435-class-exercise.mjs` and
`454-scenario-02-424-class-exercise.mjs`) against real historical SHAs, not this constructed
fixture script or its constants; neither was regenerated by this correction, and their entries

## Correction 2 (Stage 2 audit #468, P2 finding)

PR #467 (the correction directly above) itself introduced a second, independent error while
fixing the first: it re-derived Scenario 8's regression count as `719/718/1` and asserted the
Stage 2 audit's `857/857/0` figure was unreproducible. Audit #468 (triggered on PR #467's own
merge commit `46313229fe951353788b9f5954a9f8a72e39d36c`) found this wrong -- the audit's
`857/857/0` was correct. Root cause: every reproduction behind both the original 454-D record
and the PR #467 correction ran on the same Windows machine with `core.autocrlf=true`, which
converts this repository's LF-stored files to CRLF on checkout; `stage2-report.test.mjs`'s
fenced-example extraction regex is `\n`-anchored and silently fails to match under that
conversion, causing the whole 139-test file to report as one failing test instead of running
normally -- not a real pre-existing defect, and not a shell-portability issue as PR #467
concluded. See Scenario 8 below for the corrected counts and full evidence. Fixed by this
correction: Scenario 8's three data-point table, its surrounding prose, the `Bugs found`
section's now-retracted "pre-existing failure" claim, and
`454-scenario-08-regression.json`'s `afterCorrection`/`afterCorrectionDeterministicControl`
blocks. No other scenario is affected -- Scenarios 1-7 do not depend on
`stage2-report.test.mjs` or `docs/stage2-audit-contract.md`.

## Scenarios 3-7: constructed fixtures (no real historical occurrence)

Run via `node docs/stage1-correction-satisfaction-proof-runs/454-constructed-fixtures-exercise.mjs`,
which is fully network-free (every `stage1RunImpl`/`compareImpl`/`checkMergeReadyImpl`/
`checkCorrectionDeltaImpl`/`ghIssueViewImpl`/`ghPrHeadImpl` dependency is injected) and writes
one JSON artifact per scenario. None of scenarios 3-6 has a real occurrence anywhere in this
repository's history (they are negative controls for shapes the repository's own process
discipline has never actually produced), and scenario 7's constructed fixture is additional
to -- not a replacement for -- the real composed-gate evidence already produced live in
scenarios 1 and 2 above.

- **Scenario 3 (unrelated change negative control):** a disposition names
  reviewed/corrected heads `A`/`B`; an unrelated commit is then pushed, producing an actual
  gated head `C` the disposition never named. Result: `HEAD_MISMATCH` ->
  composed `NO_ACTION_YET` (fails closed; the stale disposition never silently extends to the
  new head). The artifact also records an honest, explicitly-documented limitation this
  mechanism does not attempt to close: if a disposition bullet is itself written (by mistake
  or dishonestly) naming a head that already bundles unrelated content as the "corrected"
  head, the ancestry-only check (`compare` status `"ahead"`) cannot detect that by content --
  `stage1-correction-gate.mjs`'s own module comment already states this as a trust boundary,
  not a bug, matching #454's own non-goal against requiring semantic model review.
- **Scenario 4 (stale corrected-head negative control):** a satisfaction record for corrected
  head `A` is checked against a later, unrelated gated head `B`. Result: `HEAD_MISMATCH` ->
  composed `NO_ACTION_YET`.
- **Scenario 5 (no-findings + later change negative control):** the reviewed head's real
  Stage 1 response is a clean pass (no findings); a disposition nonetheless claims
  correction-satisfied against it. Result: `NOT_SATISFIED` (findings-provenance reason) ->
  composed `AMBIGUOUS` (fails closed, never silently satisfied).
- **Scenario 6 (malformed/missing provenance), two independent sub-cases:** (a) the reviewed
  head has no genuine Stage 1 response at all (`NOT_REQUESTED`) -> `NOT_SATISFIED` -> composed
  `AMBIGUOUS`; (b) the `- **Stage 1:**` bullet itself does not parse as this disposition shape
  (missing the required `(reviewed ...)` clause) -> `parseCorrectionSatisfiedDisposition`
  returns `null`, `checkCorrectionDeltaImpl` is never even invoked (confirmed by a spy that
  throws if called), and the composed gate fails closed to `AMBIGUOUS` -- corrected per a
  Stage 1 review finding on PR #459 (`docs/bounded-review-cycle.md`'s "Correction-satisfied
  disposition" section): a bullet that is clearly attempting this shape but is malformed must
  not silently collapse into the same `NO_ACTION_YET` outcome as no disposition being present
  at all. This record originally showed `NO_ACTION_YET` here, matching this mechanism's
  pre-PR-#459-correction behavior; regenerated against the corrected, actually-merged code

- **Scenario 7 (merge-gate composition, constructed):** a fully synthetic run of the complete

## Scenario 8: regression

Documented command: `node --test tools/review-watch/*.test.mjs tools/orchestration/*.test.mjs`,
run in an isolated git worktree at `149d8a1` (`main`'s tip immediately before 454-A/B/C's three
commits) for the "before" count, `3750d27` (454-B/454-C's tip) for the middle count, and the
exact merge commit for the "after" count.

**Root cause of two successive wrong counts recorded in this section, found by Stage 2 audit
#468 (P2 finding) on the PR #467 correction that itself tried to resolve audit #466's original
P2 finding about this same scenario:** every prior reproduction in this document (454-D's
original run, and the PR #467 correction's own re-verification in both bash and PowerShell) was
performed against a local Windows checkout with `core.autocrlf=true`, which rewrites this
repository's LF-stored line endings to CRLF on checkout. `tools/review-watch/stage2-report.test.mjs`
extracts two `` ```markdown `` fenced examples from `docs/stage2-audit-contract.md` § 2 with a
`\n`-anchored regex (`extractCanonicalSkeletonFence`) at module load time; against a CRLF
checkout that regex matches zero fences instead of two, the module throws synchronously during
import, and Node's test runner reports the entire 139-test file as a single failing "test"
rather than running any of its individual tests -- silently dropping 138 real tests from the
total and reporting a false "1 failure". Confirmed directly: `git cat-file -p
<commit>:docs/stage2-audit-contract.md` (reading the stored blob, unaffected by working-tree
checkout settings) is 216-for-216 LF-only at every commit checked; a `git worktree add` forced
to `-c core.autocrlf=false` for the same commits produces CRLF-free checkouts, and `node --test`
against those checkouts reports **857 tests / 857 pass / 0 fail** -- not 719/718/1 -- with zero
difference between the glob-based command and the explicit-enumeration control, and zero
difference between bash and PowerShell (all four combinations agree once line endings are
correct). This was not a shell-portability defect in the counts, as the PR #467 correction
mistakenly concluded, and not a pre-existing, unrelated test failure, as 454-D's original run
concluded -- it was a local git configuration artifact reproducing identically across two
separate investigations because both ran on the same machine. **The glob-vs-explicit-enumeration
shell-portability finding itself remains valid and is retained below** (PowerShell does not
expand the literal glob for a native executable and fails outright, `Could not find
'...\*.test.mjs'`, independent of line-ending handling) -- only the test *counts* attributed to
it were wrong.

Re-deriving all three data points against LF-correct (`-c core.autocrlf=false`) isolated
worktrees, execution context Node `v20.19.4`, Windows, both bash and PowerShell:

| - | - | - | - |
| Before (149d8a1) | 799 | 799 | 0 |
| After 454-B/454-C (3750d27) | 842 | 842 | 0 |
| After PR #459 Stage 1 correction / exact merge commit (`0a13af0` / `ddfcfa037c33c33634a88cf65d8fe841af38bdf6`) | 857 | 857 | 0 |

**43 net new passing tests from 454-B/454-C alone (799 -> 842), plus 15 further net new passing

live evidence against already-merged PR #435/#424, and the remaining 6 (3-8) on clearly-labeled
constructed fixtures or a full before/after regression run -- none silently omitted, none
