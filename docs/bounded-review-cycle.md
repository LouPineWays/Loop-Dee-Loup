# Bounded review and acceptance-audit cycle

The target repository's stricter review rules control. When it has no stricter rule and a slice is review-worthy, use this bounded cycle. One inline round is a bound on reviewer invocations, not permission to merge a known defect.

## Entry check

Before review, verify the complete slice against its acceptance criteria and controlling authority. For code, check interacting requirements, existing invariants, generalize beyond the reported symptom, and use a fast local harness when repeated external verification would be expensive. For design or architecture, define a fixed rubric, list explicit deferrals and tensions, and self-review the entire current document rather than isolated edits.

Do not attach this cycle to trivial work merely because the mechanism exists. Preserve any target-repository rule that mandates review for a category of change.

Within Loop-Dee-Loup's own repository, a PR that touches a control-plane path — any root-level `*.md` file (currently `AGENTS.md`, `CLAUDE.md`, `README.md`), any `docs/*.md`, `.github/ISSUE_TEMPLATE/*`, `.github/workflows/*.yml`, anything under `.claude/**` (session skills, launch configuration, settings — the whole directory, not an enumerated subset), `tools/check-priority-labels.mjs` (the priority-horizon label integrity check `.github/workflows/priority-labels.yml` runs, per `docs/priority-horizons.md`), `tools/local-worker/**` (the executable substrate the `local-worker` operational skill dispatches through), `tools/review-watch/**` (the executable substrate this doc's Stage 1 and Stage 2 review-watching steps dispatch through), `tools/telemetry/**` (the deterministic session-telemetry collector/reducer that `.claude/settings.json`'s hooks and statusLine wiring execute every session, and that the `spend` operational skill dispatches through, per issue #45), `tools/ldl-init/**` (the deterministic bootstrap mechanism that installs this repository's reusable machinery into a consumer repository, per `docs/consumer-contract.md`), `tools/ldl-update/**` (the conflict-safe mechanism that moves an already-initialized consumer repository to a newer Loop-Dee-Loup revision, per `docs/consumer-contract.md`), `tools/ldl-ack/**` (the durable, ownership-preserving manual-integration acknowledgement mechanism for bridge files, per `docs/consumer-contract.md`), or `tools/mcp-server/**` (the local MCP server that exposes `ldl-init`/`ldl-update` synchronization as bounded tools over stdio, per `docs/mcp-server.md`) — is never trivial for this test, regardless of diff size. These paths govern the Loop's own rules, CI gates, session skills, backlog state, and audit machinery; a one-line error in them (a stale `done.ref`, a disabled integrity check, a loosened rule) corrupts control state silently instead of failing loudly. Such a PR always gets the full cycle: Stage 1 inline review and, once merged, its own Stage 2 issue audit, matching the `audit-control-issue` template's one-PR, one-merge-commit fields — never both stages skipped, never merged clean-by-assumption without either, and never two merges sharing one Stage 2 issue.

`node tools/check-control-plane-paths.mjs` (wired into CI as the `control-plane-paths` workflow) deterministically verifies every path already listed above still resolves against the repository, guarding against the exact silent drift found by three consecutive Stage 2 audits (issues #37, #39, #41). It cannot decide whether a brand-new top-level location belongs on this list — that remains a judgment call for whoever adds it.

## Stage 1: one inline PR review round

1. Complete the slice and required local checks.
2. Freeze and record the PR head SHA.
3. Request exactly one independent inline review at that head by posting a PR comment containing `@codex review` — the same trigger mechanism as Stage 2. Check first whether it was already requested at this head. Use `node tools/review-watch/trigger.mjs --repo <owner/repo> --kind pr --number <pr> --head <head-sha>` to perform this check-then-post step deterministically rather than hand-running `gh` reads and dedup logic — it is idempotent (scoped to the given `--head`, so a stale trigger from an older head never suppresses a genuine one at the current head) and prints the trigger's bare ISO timestamp on stdout, ready to feed straight into the `poll.mjs --since` step below. If a prior trigger produced no genuine Codex response (no reply, or BLOCKED), pass `--force true` to post a fresh retry rather than treating the stale trigger as satisfied. Never use a different reviewer tool or mechanism (e.g. GitHub's own Copilot-review request) as a substitute or supplement — that is not the documented reviewer and its silence or delay does not license falling back to one. Duplicate `@codex review` invocations at the same head are parallel opinions in one round, not new rounds. The Codex reviewer this step triggers is read-only, per `AGENTS.md`'s Code Review Rules: it inspects the PR and reports findings only, and must not modify files, commit, push, or open or update a PR. A response that attempts such a mutation and is blocked by insufficient write permission is a violated reviewer-role boundary, not a request to grant the reviewer write access, and does not count as a genuine review response — retry it the same way as a silent or BLOCKED response, per this step's `--force true` handling. `trigger.mjs` mechanically enforces step 7's one-round rule across fix commits (issue #165): for `--kind pr --head <sha>`, before posting a fresh trigger it checks every endpoint this PR could hold a Codex response on for a genuine response already attributable to an *earlier* head's trigger round, and refuses to post (exit 2) if one is found — a fix commit that produces a new head does not itself authorize a new round just because per-head dedup sees no trigger at that specific head yet. This closes the gap directly observed on PR #164, where a session cycled trigger/fix-commit/re-trigger 8 times because per-head dedup alone never stopped it. This block has no automated override: `trigger.mjs` used to accept `--ack-repeat-round "<reason>"` to record a founder-authorized second round, but the executor that the block just stopped could satisfy that flag by supplying its own justification string — exactly what happened on YouTubery PR #46 (issue #211), where a self-authored "byte-identical content" rationale unlocked a second round that then found a real defect, disproving the rationale itself. The tool cannot tell a founder-authorized reason from a self-authored one, so no caller-supplied string is trusted here anymore; passing `--ack-repeat-round` is now rejected outright (exit 1). A blocked repeat-round trigger is a founder interrupt per `AGENTS.md`'s Founder interrupt conditions, not an obstacle the executor should solve autonomously: stop and report it using `AGENTS.md`'s fixed chat report formats (a Direct question if the single blocking judgment call is otherwise unforeseeable, or a Blocked handoff naming the manual action) rather than retrying, rephrasing, or otherwise attempting to satisfy the block from inside the session. Only the founder, acting outside this script — e.g. posting the `@codex review` comment by hand — may initiate a genuinely exceptional second Stage 1 round; record that decision in the parent snapshot so a later session does not ask again. `--head` is a required argument whenever `--kind pr` is given (matching every documented Stage 1 invocation above) — omitting it is rejected rather than silently skipping the cross-head block, closing the gap a second Stage 1 review round on issue #165's own PR found: an omitted `--head` combined with `--force true` would otherwise skip both the same-head dedup and the cross-head check entirely.
4. Require complete-change inspection, actionable defects only, and separation of defects from scope expansion, preference, deliberate deferral, or superseded material.
5. Verify every finding. Reject false positives with a recorded reason and deduplicate valid findings by root cause.
6. Batch all valid findings into one consolidated correction pass and rerun required checks.
7. Do not request a second inline review on that PR.
8. Before merging, check that this PR will not auto-close its work issue on merge through any GitHub closing mechanism, for a review-worthy PR: neither the PR body nor any commit message that will land on the target default branch — including the squash-merge commit message GitHub proposes or that the executor types at merge time — may use a GitHub auto-close keyword (`Closes #N`, `Fixes #N`, `Resolves #N`, or a case variant) for the work issue, and the PR must not carry a manually-linked closing reference to it added through GitHub's Development sidebar (the "this pull request closes issue #N" option) — that link closes the issue on merge regardless of PR-body or commit-message content. Run `node tools/review-watch/lifecycle-gate.mjs merge-ready --repo <owner/repo> --pr <pr> --issue <work-issue>` to check this deterministically rather than by eye alone (issue #156, after PR #154's `Fixes #151` auto-closed issue #151 on merge, ahead of its Stage 2 audit): it fetches `closingIssuesReferences` (which covers both the PR-body-keyword and Development-sidebar sources — an unexpected entry there means one of them needs correcting before merge) and scans every commit already on the PR for a closing keyword referencing the work issue, exiting non-zero (`BLOCKED_CLOSING_REFERENCE`, with the offending source and detail) if either check finds one. It cannot see an operator-edited squash-merge message typed interactively at merge time — that source still needs eyeballing by hand, same as before. Reference the work issue non-auto-closing instead (e.g. `Addresses #N` or `Implements #N`) in the PR body, edit the squash-merge commit message at merge time if it would otherwise carry a closing keyword, and remove or decline the Development-sidebar link if one is set. GitHub auto-closes an issue the moment a commit or PR body carrying a closing keyword reaches the default branch, or the moment a PR with a manually-linked closing reference merges, ahead of the Stage 2 post-merge audit — this bypasses Verdict handling below, under which the work issue is only supposed to close as part of a CLEAN Stage 2 disposition. GitHub does not offer a repository-level setting to disable auto-close-on-merge keywords or manual closing links, so this is a PR-body, commit-message, and Development-sidebar-link authorship correction, not a platform configuration one.

   Some review-worthy PRs genuinely have no gated work issue — LDL's own recurring consumer-sync PRs (e.g. those produced by the consumer-side `ldl-sync.yml` workflow LDL distributes) are review-worthy but do not naturally have a dedicated per-update implementation issue (issue #190, reproduced on `LouPineWays/YouTubery#19`, where `merge-ready` had no way to represent that and failed with an operational error instead). Pass `--issue none` in that case — an explicit sentinel, not a value inferred from an absent `--issue` — and `merge-ready` reports `MERGE_READY_NO_WORK_ISSUE` (exit 0) without inspecting any issue: there is no closing-reference invariant to check, and it must not fabricate one against an unrelated or historical issue. This is scoped narrowly to the closing-reference check alone; it does not exempt the PR from Stage 1, CI, or any other step in this cycle, and an omitted `--issue` (as opposed to the literal `none`) still fails closed with an operational error rather than silently passing as "no work issue applies."
9. Before merging, or reporting this slice as merge-ready or complete in any other way (including AGENTS.md's `CLEAN` chat format), establish the current Stage 1 state from durable evidence with `node tools/review-watch/stage1-gate.mjs --repo <owner/repo> --number <pr> --head <head-sha>` (the same frozen head from step 2). It reuses `trigger.mjs`'s dedup read and `poll.mjs`'s genuine-response matching — never a second, competing representation of whether Stage 1 happened — to compute one of four states from the PR body and comment thread: `EXEMPT` (the PR body contains an explicit `Stage 1 exemption: <reason>` line, for a PR the Entry check judged not review-worthy — this distinguishes "not required" from "forgotten" instead of collapsing both into silence), `NOT_REQUESTED` (no trigger found at this head), `PENDING` (a trigger exists but no genuine post-trigger Codex response yet), or `RESPONSE_RECEIVED` (both exist). It exits 0 for `EXEMPT`/`RESPONSE_RECEIVED` and non-zero for `NOT_REQUESTED`/`PENDING`. Do not report a review-worthy slice as CLEAN, merge-ready, or complete on any state other than `EXEMPT` or `RESPONSE_RECEIVED`, no matter how much implementation, testing, committing, and PR creation already happened — this is the mechanical stop for the exact omission independently found twice: LDL issue #32 (PR #31 merged without Stage 1 despite the rule already being documented in prose) and YouTubery issue #12 (a session completed a slice, committed, pushed, and opened the PR without ever requesting Stage 1, and only invoked it after the founder noticed and asked). Prose alone did not prevent either recurrence, so this gate is not optional ceremony redundant with AGENTS.md's existing text — it is the deterministic check that text alone failed to enforce. The gate does not evaluate whether a reported finding is valid or whether a correction actually fixes it; that remains this cycle's own steps 4-6.
10. Merge only if every valid finding is fixed, required checks and CI pass, the reviewed scope, head, and target are reverified, step 8's closing-reference check has been performed, step 9's gate returns `EXEMPT` or `RESPONSE_RECEIVED`, and no Critical defect, founder decision, security/privacy issue, data-loss risk, migration uncertainty, or other blocker remains.

If every prerequisite in step 10 is satisfied but the execution environment itself refuses or cannot perform the merge operation (e.g. a sandboxed Claude Code permission classifier blocks `gh pr merge` as a high-risk destructive action), that is a distinct state from an unresolved prerequisite: merge is authorized and mechanically ready, only its execution is unavailable in this environment. Report exactly `BLOCKED — merge authorized but execution environment refused the merge action. Next: founder performs the already-authorized merge.` per AGENTS.md's fixed BLOCKED chat format. This is a manual execution handoff, not a second founder judgment about whether the PR should merge — do not re-litigate the merge decision, weaken repository merge protections, or request broader permissions merely to work around the refusal. Before reporting this state, make the PR itself the durable record a fresh session can resume from: its body or a comment must state that Stage 1 is complete (naming the gate's `EXEMPT`/`RESPONSE_RECEIVED` result), that every other step 10 prerequisite is satisfied, that the only remaining action is executing the already-authorized merge, and that Stage 2 has not started. A fresh session resuming this PR re-runs step 9's gate and reverifies step 10's prerequisites rather than trusting a stale statement, then attempts the merge itself before falling back to the same BLOCKED handoff again if the environment still refuses.

Multiple comments produced by one invocation are one round. Fix commits are not another round. A second invocation is another round and is prohibited by default — mechanically enforced by `trigger.mjs`'s cross-head check described in step 3 above, not prose alone.

Once Stage 1 has been requested, the PR body is the durable checkpoint. Make it self-sufficient, run `spend` first if the completed session is worth measuring, and clear or hand off rather than keeping an implementation-heavy session alive through review latency. Use PR event delivery when available; do not pair it with long fallback timers that merely preserve context. When no PR event delivery is available and a disposable worker must poll instead, use `node tools/review-watch/poll.mjs --repo <owner/repo> --kind pr --number <pr> --since <trigger-time>` rather than a hand-rolled loop, for the same early-exit-on-match reason given in Stage 2 step 6.

## Stage 2: one post-merge issue audit

1. Record the exact merge commit on the target branch, not merely the PR head. Establish it from durable repository evidence — `gh pr view <pr> --repo <owner/repo> --json state,mergeCommit` reporting `state: "MERGED"` and its `mergeCommit.oid` — never from the PR head SHA, a founder's statement that they merged it, a locally inferred commit, or a merge attempt that was denied per Stage 1's environment-refused-merge case above. If `state` is not yet `MERGED`, no merge commit exists and Stage 2 must not start; that is the expected state during a Stage 1 environment-refused-merge handoff until the founder actually performs the merge.
2. Start the audit from a fresh independent context. Open one control issue containing the complete read-only audit specification, using the `audit-control-issue` issue template, filling in its `Work issue` field with the implementation issue this audit gates and its verification-checklist field with a numbered, change-specific list of checks derived from the actual diff and acceptance criteria — not generic prose. The `Work issue` field is the sole structured source `tools/review-watch/lifecycle-gate.mjs`'s post-audit check reads to know which issue a CLEAN verdict here authorizes closing (issue #156) — never infer it from the merged PR's non-closing reference text instead. Never reuse an existing non-audit issue — the original feature or slice issue, a decision form, or any other control issue, closed or open — as the Stage 2 control boundary. A prior invocation on the wrong issue is not a completed audit; open the fresh `audit-control-issue` regardless. Type the literal word `none` into `Work issue` only when the merged PR genuinely has no gated implementation issue (issue #190 — e.g. LDL's own recurring consumer-sync PRs, reproduced on `LouPineWays/YouTubery#19`); `post-audit` reads that as the explicit no-work-issue state. The field stays required rather than being left optional/blank: an operator who simply forgot to fill in a real work issue would otherwise produce GitHub's own `_No response_` marker, rendering identically to a deliberate declaration and silently stripping that issue's premature-closure protection (Stage 1 review finding on PR #197). Do not type `none` merely to avoid finding the real work issue, and do not point it at an unrelated or historical issue (e.g. the sync mechanism's own setup issue) as a substitute — that risks `post-audit` reopening or premature-closure-flagging an issue this audit was never meant to gate. For a control-plane PR (per the Entry check's path list), the checklist must include an item confirming that every workflow whose `paths:` trigger should match the diff actually shows a completed run — not merely that the file contents are correct — checked via `gh api repos/<owner>/<repo>/actions/runs?head_sha=<sha>` against the PR's frozen reviewed head SHA (the one recorded in Stage 1 step 2), not the merge commit recorded in step 1 above. Every control-plane workflow in this repository triggers only on `pull_request`, so its Actions runs are keyed to the PR branch's head SHA; the merge commit created on `main` is a distinct commit that such a workflow never runs against, so querying `head_sha=<merge-commit>` would falsely fail even a control-plane PR whose CI ran and passed correctly. This closes the gap found in issue #96: a workflow can be silently broken (e.g. a `paths:` glob that never matches) and a content-only audit will not detect it.
3. Verify the created issue body by direct read. It must survive transport intact and name the exact commit.
4. Check whether an invocation already exists, then post one separate issue comment containing `@codex review` to trigger the reviewer — never any other reviewer tool or mechanism. Use `node tools/review-watch/trigger.mjs --repo <owner/repo> --kind issue --number <issue>` to perform this check-then-post step deterministically, the same script used for the Stage 1 trigger above (omit `--head`; a fresh audit issue is opened per merge commit per step 2, so the whole thread already corresponds to one commit); it prints the trigger's bare ISO timestamp on stdout for the bounded follow-up in step 6. Per step 10 below, a prior trigger that produced no genuine response stays PENDING — pass `--force true` to post the retry rather than treating the stale trigger as satisfied. An invocation in the issue body is specification only and does not reliably start Codex. Never invoke from both places. This reviewer is read-only, per `AGENTS.md`'s Code Review Rules, the same boundary Stage 1 step 3 states for the PR review — an attempted mutation blocked by insufficient write permission is a violated reviewer-role boundary, not a request for more authority, and is handled the same as any other non-genuine response per step 10.
5. Treat posting the trigger and arranging its bounded follow-up as one atomic action. Issue audit responses are not covered by PR-only subscriptions.
6. Keep the controlling session lean. Delegate the trigger, wait, and response extraction to one disposable worker or successor context when available. That worker must wait with `node tools/review-watch/poll.mjs --repo <owner/repo> --kind issue --number <issue> --since <trigger-time>` (see the script's header comment for full usage) rather than a hand-rolled polling loop — the script exits the instant a genuine post-trigger Codex response appears, instead of only after a fixed timeout window, so a `run_in_background` invocation's completion notification fires at match time. This is a structural fix for the defect in issue #53, where a hand-rolled loop kept re-confirming an already-captured response for 11 minutes because it had no early-exit-on-match logic and nothing ever read its output. The worker reads the matched response in its own context and returns only the verdict, severity counts, and finding text required for action. Do not load the full audit transcript, verification-command list, or evidence prose into the orchestrator merely to learn whether Codex replied. The moment that worker extracts the verdict, it must call a push-notification tool with the terse CLEAN/NOT CLEAN line, independent of whether the controlling session is still live — issue-comment audit replies have no event/webhook delivery, and the controlling session is expected to have already cleared per `AGENTS.md`'s Context-cost boundaries, so a chat message alone is not a reliable notification path.
7. Audit the exact merged commit and complete current files, applicable instructions, source-of-truth hierarchy, merged PR, and its single inline review.
8. Verify every valid inline finding's disposition and search for cross-file contradictions, regressions, missing transitions, authority conflicts, unhandled boundaries, and traps exposed by the consolidated fix.
9. Deduplicate by root cause. Report in the template's required structure: a severity table, one entry per finding with exact evidence, consequence, and smallest correction, a verification-performed checklist working through every item in the control issue's verification checklist with its result, whether founder judgment is required, and an explicit CLEAN or NOT CLEAN verdict. Modify nothing — the same reviewer-only boundary set out in `AGENTS.md`'s Code Review Rules, which Stage 1 step 3 states for the PR review.
10. Never record a CLEAN or NOT CLEAN verdict without an actual audit response comment behind it. If Codex does not respond, replies BLOCKED, or the trigger otherwise fails, the verdict stays PENDING — that is a blocker to retry, re-trigger, or escalate to the founder, not license for the controlling session or extracting worker to self-declare a verdict from its own read of the diff.

A report that nothing material remains is a successful audit. State anything the environment could not verify instead of implying it passed. PENDING is not a verdict: an audit issue with no genuine Codex response is an unfinished audit, not a clean one.

## Verdict handling

Once a genuine audit response has landed (Stage 2 step 10), first record its actual verdict in the audit issue's `Verdict` dropdown field — this is the durable evidence everything below reads, not a step to skip or defer. Only then run `node tools/review-watch/lifecycle-gate.mjs post-audit --repo <owner/repo> --audit-issue <audit-issue>` (issue #156) before acting on it: run it against the response-backed field, not before that field is updated, or it can only ever see whatever value the field already held (typically still PENDING) and never actually authorize or verify the closing transition. It reads the audit issue's own `Work issue` and `Verdict` fields — never a second, separately-tracked mapping — and additionally requires a CLEAN reading to be backed by a genuine post-trigger Codex response on that issue's own thread before trusting it, not merely the dropdown value by itself. It reports one of: `OK` (current open/closed state already matches the verdict), `READY_TO_CLOSE` (a response-backed CLEAN verdict is recorded and the work issue is still open — safe to close now), or `PREMATURE_CLOSURE` (the work issue is already closed despite no verified CLEAN verdict on record — see Premature-closure recovery below).

CLEAN closes the review cycle once `lifecycle-gate.mjs post-audit` reports `READY_TO_CLOSE`. Close the audit issue and implemented work issue where target-repository policy requires it, record the exact merge and audit evidence in the parent snapshot, and stop at this natural fresh-session boundary. The work issue closes here, on a CLEAN Stage 2 verdict — not automatically at merge; see Stage 1 step 8 on avoiding PR-body, commit-message, and manually-linked Development-sidebar auto-close references that would preempt this.

Treat every reported state other than a verified `OK` as the cycle still being open — including `PENDING`, `NOT CLEAN`, a missing/malformed verdict, and a `CLEAN` dropdown value not backed by a genuine response (each of these can also surface as plain `OK`, since the gate only distinguishes states that need action from ones that don't; none of them means the work issue is correctly done). Only `OK` with a verified `verdict: "CLEAN"` and `workIssueState: "CLOSED"` reflects the work-issue-closure half of the invariant already being satisfied. Even then, that state alone does not mean every closure step is finished: the gate never checks whether the audit issue itself is closed or whether the parent snapshot records the merge/audit evidence, so a session resuming into exactly that combination (e.g. after a prior session closed the work issue and then stopped or crashed) must still verify or complete those remaining steps before treating the cycle as fully wrapped up, not stop merely because this one gate reported `OK` (Stage 1 review findings on PR #188).

When the audit's `Work issue` field explicitly declares no work issue applies (issue #190), `post-audit` reports `workIssue: null` throughout and never fetches or acts on any implementation issue. `PENDING`, `NOT CLEAN`, and an unbacked `CLEAN` all still report plain `OK` there — non-accepted, same as with a real work issue — and a genuine response-backed `CLEAN` reports the distinct `ACCEPTED_NO_WORK_ISSUE` instead of `READY_TO_CLOSE`, since there is nothing to close: record the merge and audit evidence in the parent snapshot and stop, the same natural boundary as a `READY_TO_CLOSE`/work-issue-close cycle, just with no issue-close step.

NOT CLEAN starts one consolidated correction outcome:

1. verify each finding against the audited merge commit;
2. reject false positives and duplicates with reasons;
3. stop only for a genuine founder decision or safety blocker;
4. batch accepted findings into one correction PR;
5. run that correction through the same one-inline-round, one-audit cycle.

Do not ask routine permission between those mechanically authorized steps and do not answer findings one at a time. A correction cycle may repeat after a genuine NOT CLEAN verdict, but each cycle remains bounded and evidence-driven.

The audit advances the parent snapshot only from evidence. A reviewer's summary is not evidence by itself; verify the exact commit, files, checks, and disposition.

## Premature-closure recovery

GitHub can auto-close a work issue independently of this cycle if a closing reference slips past Stage 1 step 8 — the exact defect PR #154 produced against issue #151 (issue #156). When Stage 2 begins or resumes on an issue and `lifecycle-gate.mjs post-audit` reports `PREMATURE_CLOSURE`, that is incorrect durable state, not a completed acceptance: re-run it with `--recover true` to reopen the work issue and record a durable comment explaining why, before continuing the audit. If the environment cannot reopen it (e.g. a sandboxed permission classifier refuses the reopen), the script reports a `BLOCKED` message naming the exact manual action needed — report that verbatim per AGENTS.md's fixed BLOCKED chat format rather than treating the premature closure as accepted or reconstructing the decision from conversation history. Do not infer whether the issue should be open from anything other than this check: the audit issue's own `Work issue`/`Verdict` fields and the work issue's current state are sufficient.
