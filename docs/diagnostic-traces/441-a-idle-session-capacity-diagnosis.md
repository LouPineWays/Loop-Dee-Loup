## Reproduction protocol used

```text
open dispatched session A
-> perform no substantive work in A
-> attempt unrelated authorized Dispatch work B
-> observe whether B is blocked
```

**Access constraint discovered first:** this worker session has no tool that opens a new top-level CCD Dispatch session (no `create_session`/`start_session` MCP call is exposed — only `list_sessions`, `get_session`, `archive_session`, `stop_session`, `detach_session`, `clear_session`, `delete_session`, `unarchive_session`, `send_message`, `set_session_*`, `get_usage`, `list_events`, `export_transcript`, `search_session_transcripts`). Step "open session A" / "attempt session B" as literal UI actions therefore cannot be performed from inside this worker session — that action is only available to the founder via the CCD app itself, or possibly to a controller session with different tool grants. This worker instead reconstructed the reproduction from the two things it *could* directly execute: (1) live inspection of already-open sessions and account usage via the `ccd_session_mgmt` MCP tools, and (2) direct inspection of this repository's own orchestration source to check whether LDL's own code implements any capacity accounting at all. Both are marked below as directly observed; everything about the external product's internal slot-accounting logic is marked as inferred, since that logic is closed-source and not inspectable from this session.

## Evidence gathered (directly observed, this run)

1. **`list_sessions` (50 most recent, `include_archived: false`)** returned many sessions, all `isRunning: false`, including two sessions both titled "Issue #442" against this same repository (`local_c605bc9d-...` and `local_cf2cc819-...`, both `remoteControlActive: true`), both idle/open at the time of listing. Listing/viewing itself was never blocked or gated by the presence of these idle sessions — the call succeeded immediately and returned full data for every open session.

2. **`get_session("self")`** — called on this worker's own, literally-currently-executing session (session id `local_2c18ca5f-6983-41d0-b966-f3240522e30f`, title "Issue #442") — returned `"isRunning": false`. This is a directly observed contradiction: the session issuing the call was, at that exact moment, mid-turn and actively consuming execution (generating this very diagnostic). The `isRunning` field exposed by the CCD session-management API is therefore **not a reliable live-activity signal** — it does not track "is this session actively generating/using capacity right now" in any way this worker could detect. Any future fix that keys idle-vs-active session state off this particular `isRunning` field would be building on a flag already shown, by direct evidence, to under-report active state.

3. **`get_usage("self")`** returned account-level plan data: `plan: "Pro"`, `5-hour limit: 75% used`, `Weekly · all models: 58% used`, `extraUsage.enabled: false`. These are the only account-level "capacity" figures exposed to this session, and they are **consumption-based (tokens/messages within a rolling window)**, not session-count-based. Nothing in this response names or bounds a number of concurrently open/active sessions. An idle session sitting open does not, by itself, visibly move these percentages (they reflect this worker's own actual token usage, not the existence of sibling idle sessions).

4. **Full-text search of this repository's own orchestration/dispatch logic** — `grep -rliE "concurren|capacity|semaphore|max.?session|session.?limit|active.?slot" tools/orchestration/*.mjs tools/review-watch/*.mjs tools/ldl-init` — found **zero** implementation matches. The only hit was a code comment in `ready-dispatch-gate.mjs` about "a malformed or *concurrently-edited* manifest body" (concurrent GitHub edits, unrelated to session/process concurrency). None of `ready-dispatch-gate.mjs`, `prepare-dispatch-manifest.mjs`, `format-dispatch-prompt.mjs`, `format-unit-dispatch-prompt.mjs`, `next-review-transition-gate.mjs`, `transition-guard.mjs`, `action-envelope.mjs`, or any other file under `tools/orchestration/` or `tools/review-watch/` reads session lists, session state, process state, or any concurrency/slot counter — they operate exclusively on durable GitHub issue/comment text (Lifecycle fields, Plan Index, Dispatch Manifest). **LDL's own repository code implements no session-capacity claim, tracking, or release mechanism of any kind.**

5. **`git worktree list`** (run from `C:\Loop-Dee-Loup`) showed 11 registered worktrees under `.claude/worktrees/` still checked out, dated from **2026-08-24** (`agent-adb226215c4f4273b`) and **2026-09-05/09-06** (ten `new-session-*`/`serene-haibt-*` entries) through today (2026-09-16) with no automatic cleanup — plus 7 more temporary worktrees under `C:\Temp\ldl-recon-worktrees\` and `C:\Temp\verify-399`. These correspond to CCD-created worktrees for past sessions (several still on feature branches: `work-420`, `fix/stage2-standalone-clean-heading`, `pr424-correction`, `feature/397-transition-gates`). This is direct, objective evidence that **local worktree/process artifacts from past Dispatch sessions accumulate on disk and are not reaped when those sessions are closed** — a concrete, reproducible instance of stale local session state persisting well past the session's useful life, independent of whatever the CCD product's own backend session-slot accounting does.

## Evidence not directly reproducible from this session (inferred, clearly marked)

- Whether the founder-observed block is enforced by the CCD *desktop app process* (e.g., a hard cap on concurrently spawned local `claude` child processes/worktrees) versus the *backend/account-level Dispatch substrate* (e.g., a server-side concurrent-session quota tied to the Pro plan) cannot be distinguished from inside this session, because: (a) this worker cannot open a new top-level session to trigger the block live, and (b) the CCD app and backend are closed-source from this vantage point — no local file in this repository implements or documents that gating logic (confirmed by item 4 above: it is not in this repository at all, so it lives entirely in the external product).
- The Agent-tool documentation available to this session states that `isolation: "remote"` (cloud-dispatched subagents) "always runs in background; availability is gated" — this is the one piece of documented product behavior confirming a gating mechanism exists for at least one class of Dispatch-style session launch, but this worker did not exercise that path live (doing so would consume real external capacity/cost for a unit whose contract explicitly forbids implementation and favors minimal-footprint diagnosis), so its exact trigger condition (idle-session count vs. active-session count vs. something else) is not directly witnessed here.

## Conclusion

**The capacity claim is not owned by this repository's LDL orchestration code.** Direct source inspection (evidence item 4) rules out LDL/session-launch logic as a candidate with high confidence: there is no session-count, slot, or capacity concept anywhere in `tools/orchestration/` or `tools/review-watch/` for a fix to correct. The dispatch gates this repository does control operate purely on durable GitHub state and never observe or claim a Dispatch-product execution slot.

By elimination, and consistent with the one piece of directly-documented product behavior available to this session (`isolation: "remote"` sessions being explicitly "gated"), the founder-observed block is owned by the **external Dispatch product/substrate** — the CCD app and/or its backend's own accounting of open/live session processes — not by anything this repository currently implements. This part of the conclusion is evidence-based-by-elimination plus one documented product signal, not a live-witnessed block event, per the "inferred" caveat above.

A secondary, directly observed and independently actionable finding: **local worktree/process artifacts from closed or abandoned Dispatch sessions are not being cleaned up** (evidence item 5 — 11+ stale worktrees, one over three weeks old). Whether or not this local accumulation is causally the same mechanism the external product uses to gate new session launches, it is a real, reproducible instance of "session lifecycle state that outlives the session" in this exact repository, and is the kind of narrow, LDL-side adaptation the Shared Contract's constraints point toward ("fix the earliest reliable boundary that actually owns the capacity claim... do not build a generic worktree-cleanup project unless worktree ownership is proved causal"). Per that same constraint, 441-B must not build a generalized worktree-cleanup project on this evidence alone — worktree ownership of the *capacity claim* itself is not proven here, only that stale worktrees exist as a separate, confirmed artifact of the same underlying problem (sessions not being released/reaped).

A third finding relevant to any future LDL-side adaptation: the CCD session-management API's own `isRunning` field is **not reliable** as an idle-vs-active signal (evidence item 2) — it read `false` for the literal session that produced this document while that session was actively executing. Unit 441-B should not build idle/active accounting on top of `isRunning` as exposed by `ccd_session_mgmt` tools without independently verifying it against some other, more reliable signal.

## Summary answer to the binding question (Shared Contract "Ownership note")

**Boundary owning the capacity claim: the external Dispatch substrate/product** (CCD app and/or its backend session accounting), evidenced by elimination of LDL's own code (directly observed — no capacity logic exists in this repository) plus one documented product signal (`isolation: "remote"` gating language). Not LDL/session-launch state (ruled out directly). Worktree/process ownership is a related-but-distinct, directly observed problem (stale worktrees accumulate) that is not proven to be the actual capacity-claim mechanism, and should not be assumed causal without further evidence at the 441-B implementation stage.
