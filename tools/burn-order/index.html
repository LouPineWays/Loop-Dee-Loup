The Burn Order

One global priority stack across the Loop's own process, tooling, templates and docs — never a target repository's product backlog. You don't score items, you choose between them: which would I rather have? What burns next sits on top; priority cools as you go down.

How this works

Heat is priority. Items live in six bands. The top four are the running order — read straight down for one global rank. Blocked sits outside it until its gate clears, and Done is finished work. Neither carries a rank number, because neither is something you might do next.

Finish something by moving it to Done, never by deleting it from the bands. An item in no band reads as an accident, so it gets adopted back into Wishes and quietly rejoins the backlog. A Done item records the date and the commit or PR behind it, so node tools/burn-order/verify.mjs can check the claim instead of you having to trust it — work with no commit behind it (a post, a submission) takes a short evidence line instead.

You rank by pairwise choice, not by scoring. When you add or re-rank an item, you'll get a short series of head-to-head matchups against items already in that band. It's a binary search, so placing one item costs only about log₂(n) choices, not a full re-sort. Ask yourself, each time:

90 days from now, which would I most regret not having done?
Which one makes the most other work easier, safer, or unnecessary?

Those two questions surface durable value and option-value, instead of whichever item is shiniest today. If a matchup ever feels circular (A over B over C over A), that's a sign the items are in different currencies — split them by lane rather than forcing the order.

Two ways to order. Use the grip handle to drag a row anywhere, including into another band — fast, good for obvious nudges. Use ⟲ re-rank for the deliberate pairwise pass when you genuinely don't know where something belongs. Dragging is switched off while a search or lane filter is active, because position relative to hidden rows would be ambiguous.

Where this lives. The order is one file, docs/burn-order.json, in the repo. Every change writes straight to it, so git records the history and a Claude Code session can read the current order without you copying anything. Edit the file by hand if you prefer: this page notices within a couple of seconds and reloads. Undo steps back through this session's changes.
