One inline `@codex review` round at frozen head `82651b3c8026ba118bb3bbf22c1dee6a09d27670`: https://github.com/LouPineWays/Loop-Dee-Loup/pull/333#pullrequestreview-5102580496 (plus 3 inline comments). All three findings were valid and fixed in commit `63f8bcc`, then merged unchanged:

- **P2 — Require an explicit READY verdict from piped input**: piped JSON omitting `state` entirely (but still carrying controlIssue/executionIssue/route) fell through the original `parsed.state && parsed.state !== "READY_TO_DISPATCH"` check and was formatted into a dispatch prompt anyway. Fixed by requiring `parsed.state === "READY_TO_DISPATCH"` exactly, rejecting a missing state the same as any other non-ready value.
- **P2 — Reject malformed explicit issue numbers**: the explicit-flags CLI path only checked `controlIssue == null` / `executionIssue == null`, which does not catch `NaN`, negative, or non-integral `Number(...)` results (e.g. `Number("abc")`, `Number("-7")`, `Number("12.5")`), letting a mistyped argument produce a reference like `#NaN` that callers would use verbatim. Fixed by adding an `isPositiveInteger` check inside `formatDispatchPrompt` itself (single point of enforcement for both the piped and explicit-flags paths).
- **P1 — Avoid turning legacy routing workers into executors**: the module's own usage comment advertised the explicit-flags path as suitable "e.g. for a legacy-unsplit routing worker's own compact projection," but the fixed template always says "Implementation worker dispatch" and instructs the worker to execute the issue and report a Slice handoff — the opposite of a routing worker's actual job (return only a compact projection, never begin implementation). Fixed by removing that usage claim and documenting explicitly that this formatter is scoped to implementation-worker dispatch only, never a routing-worker dispatch.
