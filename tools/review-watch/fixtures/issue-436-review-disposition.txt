P1 "Close the gated work issue before stopping" — `STAGE2_CLOSE_READY`'s `nextCommand` only ran `close-audit`, which deliberately never touches the gated work issue, so a CLEAN cycle left the work issue open indefinitely. Fixed: a new `close-work-issue` subcommand/predicate (`checkCloseWorkIssue`, `tools/review-watch/lifecycle-gate.mjs`) closes the work issue with a durable comment; `resolvePostMergeVerdict`'s `READY_TO_CLOSE` branch chains it before `close-audit` whenever `postAudit.workIssue` is a real number, while `ACCEPTED_NO_WORK_ISSUE` keeps its audit-only `nextCommand` unchanged.
2. P1 "Route already-consumed CLEAN audits to close-audit" — the motivating resume case (work issue already closed, its backed-CLEAN audit never consumed) reaches `checkPostAudit`'s generic `OK` state, never `READY_TO_CLOSE`, and previously fell through to `NO_ACTION_YET`. Fixed: `resolvePostMergeVerdict`'s `OK` branch now routes `verdict: "CLEAN"` + `workIssueState: "CLOSED"` to `STAGE2_CLOSE_READY` with an audit-only `nextCommand`.
3. P2 "Classify closed audit issues before the open-state guard" — a directly-dispatched, already-closed canonical Audit Issue hit `checkReadyDispatch`'s `data.state !== "OPEN"` guard before ever reaching `AUDIT_ISSUE_DETECTED` classification, so it fell into generic `NOT_READY` instead of the idempotent `ALREADY_TERMINAL` route. Fixed: `checkReadyDispatch` now classifies `AUDIT_ISSUE_DETECTED` first, before the open-state guard.
4. P2 "Fetch all candidate successor audits" — `defaultGhIssueList` used a fixed `gh issue list --limit 200`, silently dropping supersession candidates once a repository's `[Audit]`-titled corpus exceeds 200. Fixed: rewritten to paginate the REST Search API (`gh api search/issues -X GET -f q=... --paginate --slurp`), recovering every candidate up to GitHub Search's own 1,000-result ceiling; new `normalizeSearchIssuesPage` helper maps the REST shape into `checkCloseAudit`'s expected candidate shape and filters out pull requests.
